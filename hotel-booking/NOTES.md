### Волна 11 «Хост в сети и порты» — СДЕЛАНО 2026-09-12
Вопрос владельца: что будет при смене IP хоста или роутера и если порты заняты. Ответ был
«связь теряется, адрес вбивают руками на каждом рабочем месте» (аудит D8-014) и «занятый порт
выглядит как “сервер дважды завершился”, а порт Postgres 5433 зашит» (D8-023). Решения — в
`docs/decisions/desktop-and-ops.md` → «Поиск хоста в сети, порты и брандмауэр».
- **Личность установки в базе:** `HotelSettings.instanceId/instancePublicKey/instancePrivateKey`
  (Ed25519, миграция `20260911190910_instance_identity`, применена к dev-базе 12.09), создаётся
  сервером при старте (`utils/instanceIdentity.js`, кэш 30 с, при лежащей базе — последняя
  известная). Переезжает на новый ноутбук вместе с копией. `GET /api/hotel` — по белому списку
  `PUBLIC_FIELDS` (`hotelController.js`), приватный ключ наружу не выходит.
- **Поиск хоста:** ответчик UDP 4781 в процессе сервера (`src/discovery/udpResponder.js`, только
  при env `DISCOVERY_PORT` — его ставит Electron-хост); клиентская сторона — `electron/lib/
  discovery.js` + сторож в `main.js` (health каждые 15 с, два отказа → `find` по сети каждые
  10 с, подтверждение подписью в `GET /api/health?nonce=…`, затем `writeConfig` + `app.relaunch`).
  Доверие при первом знакомстве: `cfg.hostInstance = { id, publicKey }` при настройке или первом
  удачном опросе. В «Настройке системы» кнопка «Найти в сети» (`config:discover`).
- **Порты:** сервер по умолчанию **4780** в упакованной сборке (dev остаётся 3001), Postgres —
  свободный от 5433 (`electron/lib/ports.js`, `resolveDbPort`, запоминается в `cfg.dbPort`; перед
  подбором проверяется `postmaster.pid`); занятый порт сервера ловится до запуска и по коду выхода
  **3** (`EADDRINUSE` в `server.js`) — диалог «Порт N занят программой X (PID)» без цикла
  перезапусков. Существующие установки хранят свой `hostPort` в config и не меняются.
- **Брандмауэр:** установщик `perMachine: true` + `electron/installer.nsh` — правило «Roomline PMS»
  по программе (`profile=any`, через `Sysnative\netsh.exe`), покрывает TCP-порт сервера, UDP 4781 и
  приём ответов на рабочем месте. У первого клиента (установка 05.09 в профиль пользователя)
  при переустановке старую копию удалить руками; данные в `%APPDATA%` не зависят от места установки.
- Проверено: сквозной UDP-тест (обе стороны), живой прогон на клоне (кто/поиск/чужой id/чужой
  ключ/подпись health/лимит), код выхода 3 на занятом порту, `describePortOwner` назвал `node.exe`,
  `node electron/test-host.mjs` зелёный (Postgres на свободном порту). **Не проверено:** два
  ноутбука по Wi-Fi, установщик с правилом брандмауэра, переезд клиента целиком (`app.relaunch`)
  — это в «Что дальше» п. 2. Ограничение: broadcast не проходит через роутеры — хост и рабочие
  места должны быть в одной подсети.

### Переименование Qonaq → Roomline PMS (2026-09-09)
Решение владельца: продукт называется **Roomline PMS** (в узких местах — «Roomline»),
товарный знак проверен. Как решение записано в `docs/decisions/interface.md`.

**Что поменялось (то, что видит человек):** заголовок вкладки и окна, шапка приложения,
боковая панель, экран входа, мастер первого запуска, «О программе», тексты про резервную
копию («Это не файл резервной копии Roomline PMS»), автор книги Excel в экспорте отчётов,
`productName` / `shortcutName` / `description` / `author` в `electron/package.json` — то есть
установщик теперь `Roomline PMS Setup 1.0.0.exe`, а процесс — `Roomline PMS.exe`.

**Лицензия.** Новые ключи выпускаются с префиксом `ROOMLINE-` (`KEY_PREFIX`), проверка
принимает и `QONAQ-` (`LEGACY_KEY_PREFIXES`). Почему навсегда: подпись покрывает только
payload, префикс — метка для глаз, а у первого клиента на руках ключ старого образца —
«перевыпустите ключ» по телефону дороже одной строки кода. Текст файла ключа —
«Roomline PMS — лицензионный ключ». Переменные окружения: `ROOMLINE_LICENSE_KEYS_DIR`,
`ROOMLINE_LICENSE_PRIVATE_KEY`, `ROOMLINE_BUILD_DATE`; прежние `QONAQ_*` читаются как
запасные, чтобы чужой `.env` не перестал работать молча.

**Что осталось техническим и почему (не трогать):**
- `name` в `electron/package.json` — `hotel-booking-desktop`. От него `app.getPath('userData')`,
  то есть папка `%APPDATA%` → `hotel-booking-desktop` с `config.json`, паролем базы и `pgdata`.
  Сменишь — у клиента «пропадут все брони». Комментарий об этом стоит в `electron/main.js`
  у `CONFIG_PATH` (в JSON комментарий не положишь).
- `appId` `com.hotelbooking.desktop` — по нему NSIS находит установленную копию: смена
  превратила бы обновление в установку второй программы рядом.
- Имя базы `hotel_booking`, имя пакета сервера, имя файла приватного ключа
  `qonaq-license-private.pem` (это существующий файл, а не текст для человека).
- `eQonaq` в `prisma/schema.prisma` — это система МВД РК, а не наш продукт.
- `docs/archive/**` и `docs/audit-2026-09/**` не тронуты: история пишется как было.

Тесты: 67 файлов, **1159 зелёных** (+5 на префиксы ключа и переменные окружения).

### Отзыв JWT: «версия токена» у учётной записи (разведка 2026-09-04 → СДЕЛАНО 2026-09-07)
**Сделано 2026-09-07** — по плану ниже, с отличиями:
- Схема — ОДНА правка: `Admin.tokenVersion Int @default(0)` + миграция
  `20260907054315_add_admin_token_version`. Пункт плана про `init.sql` устарел
  ещё 04.09 (файла нет, см. «Правила/грабли»).
- Отзыв вынесен в `utils/sessions.js: revokeSessions(id, { reason, data })` —
  хеш пароля и версия пишутся ОДНОЙ записью, сокеты рвутся с причиной
  (`auth:revoked { reason }`). Зовут: `auth.logout`, `auth.changePassword`,
  `users.setPassword`. Сбой сокета запрос не роняет.
- `middleware/auth.js` и handshake сокета сравнивают `payload.tv ?? 0` с базой
  (401 «Сессия завершена, войдите заново» / `Session revoked`). Перепроверка
  раз в 5 минут теперь ловит и версию, поднятую мимо API.
- **Смена/сброс пароля свежий токен НЕ выдаёт**: своя сессия уходит вместе с
  чужими, вход заново — проще и однозначно; клиент показывает пояснение на
  экране входа («Пароль изменён — войдите заново…»).
- Смена роли версию не поднимает: роль на каждом запросе берётся из базы,
  а не из токена, — понижение и так действует сразу.
- Клиент: `useAuthStore.logout(reason?)` — без причины шлёт `POST /auth/logout`
  (токен передаётся явно, localStorage уже пуст), с причиной — только стирает и
  кладёт текст в `notice`; `/auth/logout` исключён из перезагрузки по 401.
  **Попутно найдено:** `onClick={logout}` в `App.tsx` и `MaintenanceGateScreen`
  передавал событие клика первым аргументом — теперь `() => logout()`.
- Кнопки «Завершить все сеансы» нет: сброс пароля сотруднику — и есть рубильник.
- Проверено: 18 юнит-тестов (`test/sessions.test.js`, `fakePrisma` научился
  `{ increment }`) и сквозной прогон на dev-базе: выход гасит «второй ноутбук»
  по REST и по сокету, отозванный токен не открывает новый сокет.
- Dev-окружение: порт 3001 на этой машине держит установленная программа —
  в `.claude/launch.json` добавлены «Hotel Server (3011)» и «Hotel Client (→3011)»,
  `vite.config.ts` берёт адрес API из `API_TARGET`.

**Проблема (из аудита 2026-06-18).** `logout` чисто клиентский — просто стирает токен
из localStorage. Украденный/скопированный токен живёт до истечения `JWT_EXPIRES_IN`
(8 ч) и работает с любой машины в сети. Сменил пароль после утечки — старый токен
всё равно действует.

**Какой вариант правильный для десктопа в локальной сети.** Из трёх вариантов
(чёрный список токенов в БД, короткий access + refresh, счётчик версий токена)
для нашего случая подходит **счётчик версий** — и вот почему:
- **Чёрный список (blacklist/jti)** — нужна таблица, чистка просроченных записей
  по cron и лишний запрос на каждый вызов API. Оверкилл для 5–15 сотрудников.
- **Access+refresh** — переписывать весь клиентский слой авторизации
  (`api/client.ts`, интерцепторы, гонки при обновлении токена). Смысл имеет
  в публичном вебе, а не в локальной сети без интернета.
- **Счётчик версий (`tokenVersion`)** — ~30 строк, ноль лишних запросов
  (см. ниже), понятная семантика: «выйти на всех устройствах».

**Почему это дёшево именно у нас.** `middleware/auth.js` **уже** ходит в базу на
каждом запросе (`prisma.admin.findUnique` за `isActive` и ролью). Значит проверка
версии — это одно лишнее поле в `select` и одно сравнение, без нового запроса.

**Что нужно в схеме** (владелец схемы — другой агент, поэтому только описание):
- `Admin.tokenVersion Int @default(0)` в `server/prisma/schema.prisma`;
- та же колонка руками в `electron/db/init.sql` (миграций нет, свежая установка
  разворачивается оттуда — правило «новая колонка = ДВЕ правки»).

**Где править код** (после того как поле появится):
1. `controllers/authController.js` → `signToken()`: добавить в payload `tv: admin.tokenVersion`.
2. `controllers/setupController.js` → там своя копия `signToken()` (продублирована
   намеренно) — добавить `tv` и туда, иначе авто-вход после мастера сломается.
3. `middleware/auth.js` → в `select` добавить `tokenVersion`, после проверки
   `isActive` сравнить `payload.tv !== admin.tokenVersion` → 401 «Сессия завершена,
   войдите заново». Токены, выпущенные до внедрения, не содержат `tv` —
   считать `payload.tv ?? 0`, иначе после обновления разлогинятся все сразу.
4. `socket/socketManager.js:20` → сейчас в handshake только `jwt.verify`, **без**
   похода в базу: отозванный токен по-прежнему откроет сокет и будет получать
   обновления грида. Middleware сделать `async` и проверять `tokenVersion` и
   `isActive` так же, как REST. Плюс закрыть уже открытые сокеты пользователя.
5. Инкремент `tokenVersion` в трёх местах: `authController.logout` (выход),
   `authController.changePassword` и `userController.setPassword` (смена/сброс
   пароля обязаны убивать чужие сессии — иначе смена пароля после утечки
   бессмысленна). Опционально — при смене роли в `userController.update`,
   чтобы понижение прав применялось сразу, а не через 8 ч.
6. Клиент: `store/useAuthStore.ts` → `logout()` сейчас не зовёт `POST /auth/logout`
   вообще (стирает токен и всё). Нужен вызов сервера перед очисткой; 401 в ответ
   игнорировать — токен всё равно стираем.

**Побочный плюс:** появляется честная кнопка «Завершить все сеансы» в разделе
«Пользователи» — для главного администратора это и есть аварийный рубильник.

**Чего это НЕ решает:** токен, украденный за секунду до его использования, всё
равно сработает; защита от подбора `JWT_SECRET` — отдельный пункт аудита
(слабый секрет в `.env`).

### Справочник → вкладка «Гости» (2026-09-02)
**Идея:** собрать адресную книгу постояльцев из уже существующих броней — заводить
руками ничего не надо, данные копятся сами.
- **Что показывать:** карточка гостя = имя, телефон, сколько раз жил, всего ночей,
  последний визит + список его броней с переходом к ним в шахматке.
- **Ключ группировки — телефон, а не имя.** Имя пишут по-разному («Асель»,
  «Асель К.», «Асель Каримова»), номер один. По имени склеятся разные люди.
- **Что вылезет на живых данных:** номера записаны как попало (`+7 701…`, `8701…`,
  со скобками и пробелами) — для базы это разные строки, нужна нормализация при
  сравнении, иначе один гость размножится на несколько карточек.
- **Брони без телефона** (поле необязательное) в список не попадут. Показать их
  отдельной кучкой честнее, чем группировать по имени и соврать.
- **Зачем:** решает реальную боль стойки — «звонит гость, бронировал на июль».
  Сейчас найти его можно только листая шахматку. Плюс «постоянный гость, дайте скидку».
- **Оценка:** ~полдня, если не считать возню с нормализацией телефонов.

### Пресеты особенностей и меток (главное направление по оптимизатору)
**Идея (твоя):** не заставлять пользователя настраивать эффект каждой метки/особенности.
Вместо этого — заранее сделать **большую готовую библиотеку** особенностей и меток
с уже прописанными эффектами. Пользователь просто **скрывает ненужные** и пользуется
нужными. Мы один раз продумываем словарь и пресеты — клиент только вкл/выкл.
- **Почему важно:** сам алгоритм — простая часть, сложное — настройка под каждую базу.
  Пресеты снимают эту сложность для нетех-пользователя.
- **Что уже готово под это:** метки с эффектами хранятся в БД (`BookingFlag`),
  движок понимает словарь эффектов (буфер до/после, «не перемещать»).
- **Что осталось:** наполнить библиотеку пресетов; заменить «удалить» на «скрыть/показать»
  (поле `hidden`/`isActive` у метки и особенности); продумать список стандартных
  особенностей (типы кроватей, балкон, вид, этаж- only и т.д.) с эффектами по умолчанию.

### Путь оптимизатора во «флагман» (по убыванию ценности)
1. **Подбор под запрос** 🥇 — «есть на 5 ночей с 3 июля?»: мгновенный ответ + если не
   помещается, предложить микро-перестановку неподтверждённых броней. Превращает
   оптимизатор из пассивного в инструмент продаж (ловит брони, которые иначе теряются).
2. **Счётчик потерянной выручки** — «за месяц отвернули N запросов = X тенге». Нужен
   мини-журнал отказов.
3. **Подсказка при заведении брони** — класть новую бронь сразу оптимально (профилактика
   фрагментации вместо лечения).
4. **Цель = выручка, а не окна** — взвешивать окна по цене/сезону (yield management).
5. **Автопилот** — система сама держит сетку чистой, сигналит только при реальной выгоде.

### Расширение словаря эффектов меток
Те же «кубики», добавляются по одному (обработчик в движке + поле в форме метки):
- **Только этажи […]**, **Только корпуса […]**, **Требует особенность […]**.
- Каркас готов: `optimizeController.js` (буферы/pin) + `utils/flagEffects.js`.

### Правила/грабли
- **Чистая Windows без Visual C++ Redistributable** (12.09.2026, первый чужой ноутбук): `initdb`
  падал с `code: 3221225781` — не найдены `vcruntime140/msvcp140`. С 12.09 они едут в сборке
  (`electron/vcredist/` → `extraResources` → папка `bin` встроенного Postgres). На машине
  разработчика проблема не воспроизводится — библиотеки стоят в System32 вместе со студией;
  проверять по наличию файлов в сборке (`SANDBOX-CHECKLIST.md` п. 1).
- **Изменение схемы = ОДНА правка: `schema.prisma` + миграция.** (2026-09-04, было —
  две правки, см. ниже). `init.sql` больше нет: схема живёт только в
  `server/prisma/migrations/`, из них разворачивается и свежая установка,
  и обновляется база клиента, где уже есть брони.
  Порядок:
  1. правишь `server/prisma/schema.prisma`;
  2. `npm run db:migrate` из `hotel-booking/` (это `prisma migrate dev`) — создаёт
     файл миграции и применяет его к твоей базе. Нужен только файл, без применения —
     `npm run db:migrate:create`;
  3. коммитишь папку миграции ВМЕСТЕ с изменением схемы. Миграция без схемы (или
     наоборот) — это сломанное обновление у клиента;
  4. проверить состояние — `npm run db:migrate:status`.
  - **Сервер сначала остановить** (Prisma держит DLL, иначе EPERM) — однострочник
    ниже гасит только процесс на 3001.
  - **Что делает Electron при старте хоста** (`main.js` → `applyMigrations`):
    если в базе есть таблицы, но нет `_prisma_migrations` (установка, сделанная
    старым `init.sql`), сначала `migrate resolve --applied 0_init` — это только
    отметка, SQL не выполняется и данные не трогаются; затем всегда
    `migrate deploy`. Поэтому обновление программы само доводит базу клиента
    до текущей схемы.
  - **`0_init` — базовая миграция**, снятая с состояния схемы на 2026-09-04.
    Её не правят: новое всегда идёт следующей миграцией. В ней же лежит
    exclusion-constraint `booking_no_overlap` (Prisma его не умеет описать
    в `schema.prisma`) — поэтому свежая установка получает защиту от двойного
    бронирования вместе со схемой.
  - **Не-Prisma SQL** (constraint'ы, extension'ы, триггеры) дописывается прямо
    в файл миграции — Prisma выполнит его как есть.
  - **Рабочую базу разработчика** пометили применённой один раз командой
    `npm run db:migrate:baseline`. На чужой машине с базой из `db push` придётся
    сделать то же самое, иначе `migrate deploy` ответит P3005.
  - **`prisma db push` больше не используем** — он меняет базу мимо истории
    миграций, и следующий `migrate deploy` увидит расхождение.
  - `electron/db/` теперь только `seed.sql` (начальные ДАННЫЕ: админ, категории,
    метки). Схемы в нём нет.
  - В сборку Electron теперь входит `server/node_modules/prisma` (CLI) — им
    выполняется `migrate deploy`; раньше он из сборки исключался.
- ~~**Новая таблица = ДВЕ правки, а не одна.**~~ (до 2026-09-04) Миграций не было,
  проект жил на `db push`: он менял только локальную базу, а свежая установка
  разворачивалась из написанного руками `electron/db/init.sql`. После правки
  `schema.prisma` таблицу/индексы приходилось **вручную дописывать в `init.sql`**,
  иначе у нового клиента её просто не было (так делали для `Contact` 2026-09-02),
  а обновить базу у клиента с данными было нечем вообще. Закрыто переходом
  на `prisma migrate` (см. пункт выше).
- **Сервер в dev — обычный `node server.js`, не nodemon:** правки в `server/` сами
  не подхватываются, перезапускай руками. В `.claude/launch.json` есть конфиг
  «Hotel Server» (запуск из Claude Code); он же выставляет `SNAPSHOT_KEEP_AUTO=60`,
  чтобы тестовые прогоны не вытесняли твои авто-снимки (штатно хранится 15).
- **`prisma/sql/booking_no_overlap.sql` идемпотентный** (DROP IF EXISTS + ADD …
  DEFERRABLE INITIALLY IMMEDIATE), применять можно повторно; тот же текст в `init.sql`.
- **Пароль сисадмина** лежит в `%APPDATA%\hotel-booking-desktop\config.json`
  (`sysadmin: { salt, hash }`). Забыли — удалить **только этот ключ** из файла: окно «Настройка
  системы» откроется без пароля и попросит задать новый. **Файл целиком не удалять**: в нём
  же `dbPassword` и `jwtSecret`. С волны 7 пароль базы дублируется в
  `<pgdata>/hotel-booking-secret.json`, и потерянный `config.json` восстанавливается по нему
  (при том же `dataDir`); удалённый спутник восстанавливается из `config.json` при следующем
  удачном старте. Потеря обоих сразу = данные доступны только через `pg_hba trust` руками.
- **Проверка упакованной сборки в изоляции** (волна 7): `HOTEL_BOOKING_USERDATA=C:\Temp\hb-pack`
  в env перед запуском `electron\dist\win-unpacked\Roomline PMS.exe` — своя папка данных,
  `config.json`, лог; `APPDATA` Electron игнорирует. Заранее положить `config.json`
  `{ "mode": "host", "hostPort": 3013 }` (без BOM!), тогда сразу режим хоста без окна настроек.
  Порт Postgres с волны 11 выбирается свободный (5433, 5434, …) и пишется в `cfg.dbPort` —
  установленную копию закрывать не обязательно. Закрыть «как крестиком» из PowerShell:
  `(Get-Process -Id <pid>).CloseMainWindow()`. Мастер — через `POST /api/setup/complete`.
  После проверки папку удалить (в ней данные и пароль базы). Порт сервера по умолчанию 4780;
  поиск хоста — UDP 4781 (сервер получает `DISCOVERY_PORT` от Electron; на клоне включать
  вручную: `DISCOVERY_PORT=4781 node server.js`, клиентская сторона —
  `require('./electron/lib/discovery.js').findHosts({ port: 4781, t: 'who' })`).
- **Prisma generate падает с EPERM**, если сервер запущен (держит DLL). Перед
  `npx prisma db push` / `generate` сначала останови node. Гасить ВСЕ node-процессы
  необязательно — найди тот, что слушает 3001:
  `Get-NetTCPConnection -LocalPort 3001 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }`.
- **CSS-ловушка:** `transform` на родителе делает его containing block для
  `position: fixed` детей → ломает меню/тултипы в гриде. В строках сетки позиционируем
  через `top`, не `transform`.
- **Даты `@db.Date`** хранятся как UTC-полночь. Везде используем `Date.UTC(...)` и
  рендерим с `timeZone:'UTC'`, иначе сдвиг на день.
- **Detached-сервер `node server.js` НЕ перезапускается сам** при правке кода — нужен
  ручной рестарт (nodemon только при `npm run dev` в foreground).
  Это касается и **фоновых задач**: ночной бэкап в 03:00 выполняет тот код, что был
  загружен при старте процесса. После волны 3 (переписан `utils/backup.js`) работающий
  сервер надо перезапустить, иначе ночью отработает старая версия — та, что не
  сохраняет кассу.
