Отчёты по блокам A–E. Сводные записи за сессию, поэтому лежат отдельно

### Починка блоков C, D, E (2026-09-03, вторая волна)
Три агента параллельно по разведённым файлам; проверено API-прогоном (22 проверки)
и в браузере. Не закоммичено.
- **C1. Вход.** `authenticate` различает битый токен (401) и сбой базы (503 «Сервер
  временно недоступен») — раньше секундный рестарт Postgres разлогинивал всех. Перехватчик
  401 на клиенте не трогает запросы входа и мастера; `restore()` стирает токен только
  на 401/403. Экран входа показывает текст сервера, «Сервер недоступен…» и текст лимитера.
- **C2.** Флаг «Ранний выезд» сбрасывается при открытии формы; диалог накрывает только
  форму (контейнеру дан `position: relative`).
- **C3. Права.** `POST /shifts/next-day` и `/occupancy/optimize/apply` — только
  SUPER_ADMIN/ADMIN; отмена заселённого гостя — тоже (403). В интерфейсе: контекстное меню
  прячет «Редактировать/Удалить» для закрытых броней и «Удалить» заселённого для STAFF;
  в оптимизаторе STAFF не видит «Применить»; кнопка «Следующий день» в «Аудит → Смены»
  только администраторам и с подтверждением, где написана дата.
- **C4.** У заселённого гостя нельзя поставить выезд не позже рабочей даты (иначе номер
  «освобождался» при живом госте); `checkOut` отказывает, если рабочая дата раньше заезда.
- **D1.** Мутации номеров, категорий и партнёров сбрасывают кэш сетки (`invalidateGridCache`).
- **D2. Шапка сетки.** Выходные считаются как в строках (`T12:00:00Z` + `getUTCDay`).
  Шапка осталась снаружи прокручиваемого тела, но обёрнута в `overflow: hidden` и её
  `scrollLeft` ведётся из `onScroll` тела; ширина дня считается с вычетом измеренной
  вертикальной полосы прокрутки (ResizeObserver), так что при штатных 30 днях
  горизонтального скролла нет вовсе. Вариант «шапка внутри контейнера» отвергнут:
  пришлось бы двигать абсолютный блок виртуализатора и все оверлеи.
- **D3.** `fetchGrid` нумерует запросы и применяет только ответ на последний.
- **E1. Резервные копии без pg_dump.** `utils/backup.js` — JSON-дамп всех таблиц через
  Prisma (`backup_YYYY-MM-DD_HH-mm.json` в `BACKUP_PATH`, хранится `BACKUP_KEEP`=14,
  запись в `BackupLog`). Восстановление `POST /api/system/backup/restore { fileName }`
  (только SUPER_ADMIN): сначала копия текущего состояния, затем одна транзакция
  delete+createMany с сохранением id и `setval` последовательностей, сброс кэша сетки
  и `snapshot:restored`. Cron остался «03:00», но по `BACKUP_TZ` (по умолчанию Asia/Almaty),
  а не по UTC сервера. Настройки → «Бэкап»: последняя копия и статус, «Сделать копию
  сейчас», список файлов, «Восстановить». Проверено вживую: копия 733 КБ, откат
  из неё воспроизводит базу один в один.
- **E2. Electron.** Признак «схема накатана» — файл `schema-ready.json` в папке данных,
  пишется после успешного init.sql+seed; старая установка без отметки проверяется по
  наличию базы `hotel_booking`; провал init — база дропается, чтобы не остаться пустой
  «готовой». Ошибки Postgres без текста получили понятное сообщение с путём к логу.
  Упавший сервер перезапускается один раз, при повторном падении — диалог и окно
  настроек. В dev — свой userData (`…-dev`) и правильные пути к `electron/db` и `server/`.
- **E3. Обновления.** `electron-updater` (generic-провайдер, адрес — `updateUrl`
  в `config.json`, поле «Сервер обновлений» в «Настройке системы»); тихая проверка
  через 30 с и раз в сутки; Настройки → «О программе»: версия, «Проверить», «Скачать»,
  «Установить и перезапустить». Реальный сервер обновлений с `latest.yml` ещё не поднят.
- **E4. Журнал действий.** Модель `AuditLog` (+ `init.sql`), middleware `audit.js`
  на все мутации броней, смен, оптимизатора, снимков, пользователей, фонда, тарифов
  и бэкапов: кто, что, объект, детали без паролей. `GET /api/audit/log` и вкладка
  «Действия» в «Аудите» с фильтром по сотруднику и датам. Окно «Аудит» переведено
  на токены темы (в тёмной теме больше не белое).
- **E5.** «Отчёты» убраны из меню; поиск в шахматке ищет и по цифрам телефона
  (`regexp_replace` в `$queryRaw`); шапка при окне < 900px прячет название и бейдж.

### Починка блоков A и B + мастер первого запуска (2026-09-03)
По отчёту «main problems» (папка «Qonaq — документы») закрыты блоки A и B; делали четырьмя
агентами параллельно (файлы разведены, чтобы не пересекались), проверено API-прогоном
(27 проверок) и в браузере. Все правки не закоммичены — лежат в рабочей копии.
- **A1. Редактирование брони больше не обнуляет деньги.** Сетка отдаёт бронь целиком
  (гости, скидка, суммы), а форма при открытии всегда догружает бронь с сервера
  (`fetchBooking`) и держит «Сохранить» заблокированной, пока грузится.
- **A2. Итог не пересчитывается без причины.** В режиме правки сумма уходит на сервер,
  только если изменились входы калькулятора (даты, категория, гости, скидка, предоплата)
  или нажата «Пересчитать по тарифу»; иначе справа «Сохранённая сумма брони». Категория
  без тарифа → «итог не рассчитан» (ноль — не цена); ночи вне сезонов помечаются
  предупреждением. Календарь цен (`RatePrice`) к расчёту пока НЕ подключён — следующий шаг.
- **A3. Валидация и ошибки.** Числа проверяются на POST и PUT (`routes/bookings.js`),
  PUT получил те же правила, что POST; `errorHandler` переводит P2003 / P2010(23503) /
  P2000 / PrismaClientValidationError в 400 вместо 500; удаление категории считает
  и скрытые номера; `grid`/`availability`/`check-availability` валидируют query.
- **B1. Переезд со сплитом не работал никогда:** `createdById` → `adminId`; вторая часть
  наследует метки и партнёра; дата переезда не позже смены; в деактивированный номер нельзя.
- **B2. Оптимизатор применяется.** Ограничение `booking_no_overlap` пересоздано как
  `DEFERRABLE INITIALLY IMMEDIATE` (скрипт идемпотентный, применён к живой БД,
  продублирован в `init.sql`). `applyOptimization` — одна интерактивная транзакция
  с `SET CONSTRAINTS booking_no_overlap DEFERRED`; перед записью проверяет актуальность
  плана (409 «План устарел» со списком причин), пишет safety-снимок «Перед применением
  оптимизатора», после — рассылает `booking:updated`. В модалке при ошибке — «Пересчитать».
- **B3. Realtime между рабочими местами.** Единый payload `{ booking }` с `roomId` и
  `partner` (нормализация в `socketManager.emitBookingEvent`), `replaceBooking` переносит
  бронь между строками, новое событие `shift:changed` (клиент перецентрирует сетку),
  apply оптимизатора эмитит обновления. При неполном payload клиент перезагружает сетку,
  а не падает с TypeError.
- **Мастер первого запуска и системные настройки.** Две разные роли: **сисадмин** — ставит
  программу и правит подключение; его пароль хранится ЛОКАЛЬНО в `config.json` Electron
  (scrypt-хеш) и открывает только окно «Настройка системы» (режим хост/клиент, порт,
  папки данных и бэкапов, подсказка IP для клиентов). Локально — чтобы войти в настройки
  можно было и когда сервер недоступен. **Главный администратор** — владелец отеля,
  SUPER_ADMIN в базе. Меню «Файл» убрано совсем (F12/F5/Ctrl+R оставлены), в системные
  настройки — с экрана входа по паролю сисадмина. После запуска сервера, пока
  `HotelSettings.setupCompletedAt` пуст, вместо входа показывается мастер: Отель →
  Главный администратор → Сотрудники → Проверка (`POST /api/setup/complete`, публичный
  до завершения, потом 403; отдаёт токен — авто-вход). Мастер имеет приоритет над
  сохранённой сессией, чтобы сидовый admin/admin123 не обходил его. Управление
  пользователями: `/api/users` (только SUPER_ADMIN, без удаления — только `isActive`,
  нельзя деактивировать себя и последнего SUPER_ADMIN) + Настройки → «Пользователи».
  Название отеля в шапке и меню — из настроек объекта (Настройки → «Отель»), хардкод
  «Гранд Алатау / 142 номера» убран.
