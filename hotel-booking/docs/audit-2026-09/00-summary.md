## 2. Главное — 12 проблем, сгруппированных по смыслу (дубли сведены)

Порядок — по цене ошибки для отеля, не по номеру направления.

1. **[1] Мастер первого запуска переписывает главного администратора без пароля** — `POST /api/setup/complete`
   защищён только полем `HotelSettings.setupCompletedAt`. Восстановление копии без таблицы `HotelSettings`
   (или база, настроенная до появления мастера) открывает любому в сети отеля переименование
   SUPER_ADMIN `id=1` с новым паролем и выдачу токена. — D1-001; связано D8-010 (restore возвращает
   `tokenVersion` и хеши), D1-021.

2. **[1] Переезд со сплитом ломает деньги обеих частей** — кэш `paidAmount` делится по ночам, а строки
   `Payment` остаются на первой части (касса и «Долги» считают по журналу → «переплата» и «долг» на одной
   оплаченной брони); из начислений уезжают только `stay`-строки, питание и скидка остаются целиком
   (отрицательный итог первой части, двойное питание после любой пересборки второй). **Вживую на клоне:**
   бронь с завтраками 14 000 и без посуточных строк (цен на эти даты нет) после сплита дала 14 000 у
   закрытой части + 7 000 у новой без единой строки = 21 000 — `keepIfEmpty` оставляет второй части
   пропорцию, пока все строки остаются на первой. — D7-013 [1], D3-001 ≡ D2-004, D3-002, D2-008.
   Пункт NOTES «сплит делит деньги» [x] — **регресс** (закрыт до появления журнала платежей и строк по видам).

3. **[2] Возврат без исходного платежа и без лимита, доступен STAFF** — `POST /payments` с видом `refund`
   не требует `refundOfId` и не сравнивает с принятым; именно этот путь зовёт кнопка «Возврат» рядом с
   «Принять», сумма предзаполнена долгом, подтверждения нет. — D2-001 ≡ D1-002, D6-011. Решение
   `data-and-money.md:62` покрывает только приём и отмену.

4. **[2] Ранний выезд и отмена не трогают деньги** — «Выезд» раньше срока укорачивает `checkOut`, но
   stay-строки за непрожитые ночи остаются (ложный долг, панель начислений закрытой брони read-only);
   `cancel` только меняет статус — отменённая бронь с предоплатой исчезает из «Долгов/переплат» и
   штраф записать некуда. — D2-002 ≡ D3-005, D2-006, D4-005, D7-007.

5. **[2] Встроенный Postgres в упаковке создан с `--locale=C`** — `ILIKE` и `mode: insensitive` не сворачивают
   регистр кириллицы: «асель» не находит «Асель» в шахматке и кассе. В dev-базе (`Russian_Kazakhstan.1251`)
   дефект невидим; кластер первого клиента (05.09) уже создан с `C`, смена локали = пересоздание кластера.
   — D8-001 (подтверждено SQL с `COLLATE "C"`).

6. **[2] Предпросмотр формы и сервер считают разные итоги** — база скидки (клиент: проживание; сервер:
   все строки включая ручные), ключ пересчёта клиента шире серверного (правка только предоплаты/льготников
   записывает клиентский `totalAmount` без пересборки строк → `totalAmount ≠ Σ BookingCharge`), ночь с
   частично заполненной ценой начисляется частично и молча. Вживую: скидка % + ручная строка → форма
   показывает 106 000 и 99 900, сервер сохраняет 94 900. — D5-002 ≡ D2-007, D2-003, D7-009.

7. **[2] Квоты партнёров работают как «предупреждение при каждом сохранении»** — `Booking.partnerId`
   никогда не записывается (create/update его не пишут), поэтому любая бронь в квотном номере получает
   `409 ALLOTMENT_CONFLICT` при каждом `PUT`; из формы брони продажа «поверх квоты» вообще недостижима
   (кнопка гасится по любой причине недоступности, `AllotmentConfirm` появляется только через Enter);
   оптимизатор квоты не видит вовсе. — D3-003, D5-001 ≡ D7-005, D3-007. NOTES «Аллотменты защищены» [x] —
   **частично**.

8. **[2] Эксплуатация упакованной программы: пять сценариев без выхода** — ночная копия только пока
   программа запущена, пропуски не догоняются (D8-003); единственная копия пароля базы — `config.json`,
   перезаписываемый неатомарно при каждом старте (D8-004); падение Postgres не замечается, закрытие
   после него зависает, повторный запуск гасится single-instance (D8-002, предположение по коду); упавшая
   миграция P3009 блокирует запуск навсегда, откат установщика не помогает (D8-005); полный диск — каскад
   до зависания (D8-006). Плюс `electron/dist` устарел: установленная сборка без отзыва JWT (D8-021).

9. **[2] Права STAFF шире, чем где-либо записано** — правит `totalAmount/paidAmount/discountPercent/shiftId`
   через `PUT /bookings/:id` и удаляет строки начислений без следа суммы в журнале (D1-003 ≡ D2-005),
   создаёт ручные снимки (D1-015), видит книгу гостей с документами и выгружает реестры (D1-006),
   запускает расчёт оптимизатора. Клиент ничего не прячет — расхождений «клиент прячет, сервер пускает»
   нет; проблема в отсутствии решения о модели прав. **Вживую под `audit-staff` (D7-012, авторы прогона
   оценили как тяжесть 1):** `GET /guests` — вся адресная книга с телефонами; `POST /reports/debts/export`
   — CSV с телефонами; `POST /reports/revenue/run` — 200; `POST /snapshots` — снимок создан;
   `PUT /bookings/173 {paidAmount: 99999}` — кэш разошёлся с журналом, «Аудит → Сегодня» показал
   «Оплачено 129 999».

10. **[2] Персональные данные оседают вне базы** — каждый запрос логируется с query-строкой
    (`guestSearch=`, `lookup?phone=`, `debts?q=`) в `combined.log` и `host-debug.log` без ротации
    (dev: 104 строки с ФИО/телефонами); `AuditLog.details` хранит тела запросов с номерами документов
    бессрочно; сокет переживает срок жизни токена и рассылает полные брони с паспортными данными всем
    подключённым. — D1-004 ≡ D8-008, D1-007, D1-005.

11. **[2] Переходы статусов: три дыры** — `checkin` без верхней границы (можно «заселить» бронь с прошедшим
    выездом → тупик «Следующего дня»), `NO_SHOW` никогда не ставится (незаезды держат номер в constraint
    весь срок, метрика «Доля незаездов» всегда 0), walk-in «Заезд» из шахматки создаёт CHECKED_IN без
    `actualCheckInAt` (самый частый путь). — D3-004, D3-006, D7-004.

12. **[2] Отчёты и экспорт** — кнопка «Excel» даёт 500 на названии с `: / \ ? * [ ]` (D4-001, зонд);
    CSV не нейтрализует формулы `= + - @` из имени гостя/заметки (D4-002); формула из 10 000 слагаемых
    проходит валидацию и роняет каждый запуск сохранённого отчёта (D4-003, зонд); «Дата создания» и
    «Календарная дата приёма» — по UTC, для UTC+5 ночные операции уезжают на вчера (D4-004).

## 4. Сквозная модель времени (собрано из 2/3/4/5/6/7/8)

Одна и та же «дата» в проекте бывает пяти видов, и они смешиваются:

| Источник | Где верно | Где течёт |
|---|---|---|
| Бизнес-дата (дата смены, из БД) | `create/update/checkin/checkout`, `/occupancy/grid`, финансовые отчёты «по смене», `Payment.businessDate` | `todayUTC()` при посеве первой смены берёт день по UTC (NOTES, открыто) |
| `@db.Date` как UTC-полночь | вся шахматка, начисления, квоты | клиентские календари открываются на месяце устройства (D7-008); первый запрос грида — с датой устройства, потом перезапрос (D7-003, D5-007) |
| Моменты `DateTime` (`createdAt`, `paidAt`, `actualCheckInAt`) | экран показывает местное время (`format.ts`, `BookingModal`) | производные «Дата создания»/«Календарная дата приёма» и период «по дате создания» — по UTC-календарю (D4-004); штампы в файлах выгрузки — UTC (D4-012); окно «Аудит» «Сегодня/7 дней/Месяц» — от `new Date()` сервера при `TZ=UTC` (D6-003); `/occupancy/stats` — по дате устройства (D3-020) |
| Часы устройства как fallback | — | `useGridStore` до ответа сервера, `BookingGrid.tsx:161`, `BookingModal.tsx:1357` — двумя разными календарями (D5-008); `AuditWindow` разбирает дату в местной зоне и шлёт UTC (D6) |
| Часовой пояс задач | ночная копия по `BACKUP_TZ` (из локали машины хоста, фолбэк Алматы) | `TZ` принудительно UTC (`server.js:4`); платёж всегда в текущую смену — «вчерашнюю» оплату после перехода дня не провести вчерашним днём (D2-021) |

Вывод: денежные отчёты «по смене» и шахматка — согласованы; всё, что производится от `DateTime`
(создание, приём по часам, аудит-окно, статистика), живёт по UTC и расходится с тем, что видит стойка
в UTC+5/+6 между полуночью и 05:00.

## 5. Что в порядке (сводно, чтобы не перепроверять)

- **Данные:** инварианты живой базы держатся (см. §1); `booking_no_overlap` DEFERRABLE + `btree_gist 1.7`;
  все 7 raw-SQL — тегированные шаблоны или константы, инъекций нет; sequences ≥ `max(id)`.
- **Доступ:** отзыв JWT через `tokenVersion` работает по REST и по сокету (подтверждено вживую — сц. 1);
  лицензия не снимается мусорным ключом; traversal в копиях закрыт; `webPreferences`/preload Electron —
  как заявлено; XSS-sink'ов в клиенте нет; логин не различает «нет юзера»/«неверный пароль».
- **Деньги:** «начислено/принято/долг» считаются одним `bookingMoney.js` в кассе и отчётах; `refund` по
  платежу ограничен остатком; void платежа с возвратами запрещён; порядок «сначала возвраты» соблюдён.
- **Отчёты:** архитектура «отчёт = данные» выдерживает — SQL из определения не собрать, `eval` нет; пресеты
  периода от бизнес-даты; итоги сгруппированных отчётов от всех строк; `financeReports` 19/19.
- **Копии/снимки:** формат v2 с деньгами, восстановление в транзакции; гейт на потерю платежей и галочка
  `allowMoneyLoss`/`allowDataLoss` действительно обязательны в обоих окнах (D6 §2); `Snapshot` переживает restore.
- **Desktop:** встроенный Postgres — только loopback (`listen_addresses` умолчание, `pg_hba` 127.0.0.1/::1);
  `requestSingleInstanceLock`; `missingBaselineTables` отказывает до любых изменений.
- **Качество:** 402 теста зелёные (1,7 с), `tsc --noEmit` без ошибок при `strict`; локальных `new Date(y,m,d)`
  в клиенте нет; `window.prompt` устранён; `dangerouslySetInnerHTML` = 0.

## 6. Решения, которые нужны от владельца (не код)

Сгруппированы; ссылки — на вопросы в отчётах.

**Деньги и стойка**
1. Модель прав STAFF: возвраты (в т. ч. «свободный»), правка сумм и удаление строк, ручные снимки, книга
   гостей с документами, выгрузка отчётов — что из этого «да» (D1 §6.1, D4 §6.5).
2. Ранний выезд: брать за фактические ночи (тогда `checkout` пересобирает строки) или за весь срок
   (тогда записать в решения, что `roomNights ≠ charges`) (D3 §6.1). Поздний заезд — аналогично (D3 §6.2).
3. Отменённая бронь с деньгами: штраф за отмену, показ в «долгах/переплатах» до возврата, отчёт «кому
   вернуть» (D2 §6.2, D4 §6.1).
4. Сплит переезда: переносить ли платежи и строки питания пропорционально или «вторая часть — бесплатное
   продолжение с долгом 0» (D3 §6.5). Переселение в другую категорию — бесплатно или по новой цене (D3 §6.6).
5. Незаезд: нужен ли переход `NO_SHOW` (кнопка/автомат при «Следующем дне»); до тех пор — убрать метрику
   и фильтр из поставки (D3 §6.3, D4 §6.7).
6. Партнёрские брони: поле партнёра в форме или квоты = только предупреждение (тогда подтверждение при
   каждом сохранении — ошибка) (D3 §6.4, D5 §6.1). Квотные номера и оптимизатор (D3 §6.9).

## 7. Живой прогон (направление 7) — что показал браузер

Все 12 сценариев пройдены на клоне (~2,5 ч машинного времени); «Печать» и «Отчёты» — частично:

отката снимка/копии с деньгами требуют галочку и делают защитные копии; `refundOfId` восстанавливается;
приём/возврат/отмена платежа из формы; `AllotmentConfirm` недостижим из формы новой брони (D7-005 ≡
D5-001); три разных итога при скидке + ручной строке — 106 000 / 99 900 на экране, 94 900 в базе
(D7-009 ≡ D5-002); «Касса» на втором рабочем месте не видит платежи коллеги до перезахода в раздел
(D7-010 ≡ D6-001); права STAFF (D7-012); сплит удваивает начисления (D7-013, новое).

**Новое, чего статика не видела:** walk-in «Заезд» из шахматки создаёт CHECKED_IN без `actualCheckInAt`
— пункт 1.0 № 2 выполняется только для «бронь заранее → кнопка Заезд» (D7-004); 401 посреди формы —
перезагрузка без пояснения, ввод потерян (D7-002); «Очистить период» в тарифах без подтверждения при
предвыбранных всех категориях и месяце устройства (D7-011); окно «Переезд гостя» подсказывает даты до
`checkOut−1`, сервер разрешает только не позже бизнес-даты (D7-006); диалоги «Удалить бронь?» обещают
удаление, а сервер ставит CANCELLED (D7-007); календари открываются на месяце устройства (D7-008);
двойной клик «Создать бронь» — два `POST`, спасает только 409 сервера (D7-014); восстановление копии
откатывает и журнал действий (D7-015); origin `[::1]` отвергается CORS как 500 (D7-001, только dev).

**Тексты сервера хорошие, форма их прячет:** 409/400 для пересечения, буфера метки, квоты, нулевой ночи
и прошлого — содержательны; форма новой брони показывает вместо них «Номер занят» и блокирует кнопку.
