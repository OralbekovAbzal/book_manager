# Десктоп и эксплуатация — принятые решения

Electron, режим хост/клиент, бэкапы, обновления, мастер первого запуска.
Живая часть журнала — в `hotel-booking/NOTES.md`.

### Поиск хоста в сети, порты и брандмауэр (2026-09-11, волна 11)
**Вопрос владельца:** что будет, если у хоста сменится IP или роутер, и если порты заняты.
Было: адрес хоста лежит в `config.json` рабочего места, при смене адреса его вбивают руками под
паролем сисадмина на каждом ноутбуке (аудит D8-014); занятый порт сервера показывался как
«сервер дважды завершился», порт Postgres 5433 зашит (D8-023). Решения:
- **Рабочее место находит хост само.** Хост отвечает на широковещательный UDP-запрос (порт 4781),
  рабочее место после двух неудачных опросов `/api/health` спрашивает сеть, где его хост, и,
  найдя, переписывает адрес в `config.json` и перезапускается («Хост найден по новому адресу…»).
  В «Настройке системы» режима «Клиент» есть кнопка «Найти в сети». Ограничение, принятое
  осознанно: широковещание не проходит через роутеры — хост и рабочие места должны быть в одной
  подсети; это и есть модель «одна сеть гостиницы».
- **Личность хоста живёт в базе, не в `config.json`.** `HotelSettings.instanceId` + пара Ed25519.
  Так она переезжает на новый ноутбук вместе с резервной копией, и после переноса (см. «Перенос
  на новый ноутбук…») рабочие места находят хост сами; войти придётся заново (`jwtSecret`
  остаётся в config). Цена: приватный ключ попадает в файл копии — того же класса секрет, что
  хеши паролей и данные гостей там же. Компенсации: ответчик отвечает только в частные сети,
  подпись покрывает `id|port|nonce`, переезд подтверждается второй подписью в `/api/health`,
  факт переезда пишется в `host-debug.log`. `GET /api/hotel` отдаёт настройки по белому списку.
- **Доверие при первом знакомстве (как SSH).** Рабочее место запоминает `id` и публичный ключ хоста
  при настройке или первом удачном подключении по адресу, который ввёл сисадмин, и дальше
  переезжает только на хост с этой личностью. Чужой хост в той же сети (вторая база отдыха того
  же владельца, гостевой Wi-Fi) увести рабочее место не может. Сменил сисадмин адрес в
  настройках — личность забывается и запоминается заново (перепривязка после переустановки хоста).
  На автоматический запрос («find» с конкретным id) хост отвечает только если ищут его; на общий
  («who», кнопка) — без названия отеля.
- **Порты.** Сервер по умолчанию **4780** (было 3001 — его любят Node-проекты и софт
  разработчика; 4780 ниже динамического диапазона Windows 49152+); dev-режим остаётся на 3001.
  Существующие установки хранят свой порт в `config.json` и не меняются — рабочие места узнают
  фактический порт из ответа хоста. **Postgres** — свободный порт от 5433, запоминается в
  `cfg.dbPort`; перед подбором проверяется `postmaster.pid` (живой процесс на записанном порту =
  «база уже запущена другой копией», а не тихий уход на 5434 с ошибкой хуже). Занятый порт сервера
  ловится до запуска и по коду выхода 3 — диалог называет программу-владельца (`netstat`/`tasklist`),
  без цикла перезапусков.
- **Брандмауэр — правило ставит установщик.** Установщик переведён на `perMachine: true`
  (права администратора при установке и обновлении) — ради одного правила по программе
  «Roomline PMS» (`profile=any`, чтобы работало и на «Общедоступной» сети). Одно правило
  покрывает TCP-порт сервера, UDP 4781 и приём ответов на рабочем месте, потому что серверный
  процесс — тот же exe в режиме node. Отвергнутый вариант: правило из программы через UAC
  при сохранении режима (установщик остался бы без прав). У первого клиента копия 05.09 стоит в
  профиле пользователя — при переустановке удалить её руками; данные в `%APPDATA%` целы.
- **Не делаем:** mDNS/Bonjour (лишняя зависимость ради того же результата); поиск через роутер
  (другая подсеть — вписать адрес руками, как раньше); автосмену порта сервера (клиенты хранят
  адрес, а без поиска не узнают новый).

### Доступ и персональные данные (2026-09-08, волна 8)
По аудиту D1-001/004/005/007, D8-007/008, D9-001. Решения владельца:
- **Мастер первого запуска — только на нетронутой базе, без «ключа хоста».** Нетронутая = учёток
  нет или одна сидовая `admin` с сидовым паролем. Отметка `setupCompletedAt` перестала быть
  единственной защитой: пропала при настоящих учётках — восстанавливается сама, мастер не
  показывается; пустая таблица учёток открывает мастер при любой отметке (войти некому). Гонка двух
  отправок снимается блокировкой строки настроек в транзакции (второй получает 409 `SETUP_DONE`).
  Вариант с одноразовым ключом от Electron отвергнут: лишняя проводка ради окна в минуты между
  установкой и мастером. Прохождение мастера пишется в лог `warn` (в журнал действий — не попадает:
  учётки в запросе ещё нет).
- **Сокет живёт не дольше токена** и не несёт документов гостей: паспорт нужен только карточке,
  а она перечитывает бронь с сервера. Причина разрыва `token_expired` показывается на входе.
- **Логи без персональных данных:** значения query не пишутся (только имена параметров), ошибки —
  первой строкой (тексты Prisma повторяют тело запроса целиком), ротация 5 МБ × 5, `host-debug.log`
  режется при старте, без ANSI. Уже накопленные логи у клиента не чистим — ротация вытеснит.
- **Журнал действий без документов, с чисткой по сроку** (`AUDIT_RETENTION_DAYS`, 365 по умолчанию);
  имя и телефон остаются — без них запись «кто менял бронь кого» бессмысленна. Чистка в 03:30, после
  ночной копии, чтобы удалённое осталось во вчерашнем файле.
- **Electron 44 / electron-builder 26 / node-cron 4 — обновили сейчас,** а не «после показа»:
  каждые полгода отставания добавляют версии, а проверка по рецепту изолированной сборки занимает
  минуты. electron-builder 26 отсекает корневой `node_modules` у `extraResources` — сервер
  копируется двумя FileSet'ами. Минимальную версию Windows для Chromium 152 уточнить до отгрузки.
- **Не делаем:** ключ хоста для мастера; закрытие `GET /setup/status` (нужен клиенту до входа);
  шифрование журнала; major-обновления `exceljs`/`express` ради `uuid`/`qs` (fix недоступен).

### CORS для окна на file://: сокет шлёт Origin, fetch — нет (2026-09-12)
На чистой установке после входа висела полоса «Нет связи с сервером» при живом сервере. Пробник
(Electron-окно на `file://` против http-сервера, логирующего заголовки) показал: `fetch` с
`Authorization` уходит **без** `Origin`, а WebSocket-рукопожатие — с `Origin: file://`.
`corsOrigin` пропускал только отсутствующий Origin и адреса локальной сети, поэтому REST
работал, а engine.io отвечал сокету 403; socket.io переподключался вечно, полоса (волна 9)
сделала это видимым. Решение: `file://` и `null` (опаковый origin) разрешены явно
(`OPAQUE_ORIGINS`), всё прочее — как было. Безопасность не страдает: граница — JWT, страница с
чужого `file://` до нашего `localStorage` не дотянется. Realtime между рабочими местами в
упакованной программе до этой правки не работал вовсе — обновления приходили только после
перезагрузки сетки.

### Среда выполнения Visual C++ едет в установщике (2026-09-12)
Первая установка на чужой ноутбук упала на `initdb`: код `3221225781` (`0xC0000135`, «DLL не
найдена»). Бинарники `@embedded-postgres/windows-x64` собраны MSVC и требуют `vcruntime140.dll`,
`vcruntime140_1.dll`, `msvcp140.dll`, которых в пакете нет, а на чистой Windows нет и в системе
(на машине разработчика они стоят вместе со студией — поэтому не замечали). Решение: три
подписанные Microsoft библиотеки лежат в репозитории (`electron/vcredist/`, README там) и
`extraResources` кладёт их рядом с `postgres.exe` — «app-local», официально разрешённый способ.
Отвергнуто: бесшумный запуск `vc_redist.x64.exe` из установщика (+25 МБ, лишний инсталлятор,
ничего не даёт сверх трёх файлов). `describeStartError` на этот код теперь называет причину.

### Упаковка: локаль, пароль базы, живучесть хоста (2026-09-08, волна 7)
По аудиту D8-001/002/004/005/006. Решения владельца и что из них вышло:
- **Локаль встроенного Postgres — builtin `C.UTF-8`, а не ICU и не пересоздание кластера.**
  Проблема: кластер создавался с libc `C`, где `ILIKE`/`lower()` сворачивают регистр только у
  латиницы — «асель» не находил «Асель». Варианты: ICU `ru-RU` (словарная сортировка, но
  зависимость от версии ICU dev↔сборка и предупреждения после обновлений), «только новые кластеры»
  (у клиента поиск сломан до переустановки). Выбрано: миграция задаёт коллацию `pg_c_utf8`
  колонкам поиска (`Booking.guestName`, `Room.number`) — чинит существующие кластеры без
  пересоздания; новые кластеры — `initdb --locale-provider=builtin --builtin-locale=C.UTF-8
  --locale=C`. Сортировка по кодовым точкам (заглавные раньше строчных, «ё» после «я») — как
  и было в упаковке; для ФИО с заглавной незаметно. Правило: новое текстовое поле, по которому
  ищут без учёта регистра, — с `COLLATE pg_c_utf8` в миграции; при смене типа колонки COLLATE
  повторить явно (Prisma коллацию не моделирует и не заметит потерю).
- **Пароль базы — спутник рядом с кластером, а не `trust`.** `--auth=trust` для loopback снял бы
  проблему целиком, но открыл бы 5433 любому Windows-аккаунту машины. Вместо этого:
  `config.json` пишется атомарно и только при изменении; пароль дублируется в
  `<pgdata>/hotel-booking-secret.json` (там же, где `schema-ready.json`); при расхождении
  побеждает спутник — он записан только после подтверждённого подключения. Кто владеет файлами
  кластера, владеет данными и так, поэтому пароль рядом с ними ничего не ослабляет.
- **Упавший Postgres поднимаем сами**, до 2 попыток с паузой 3 с; не поднялся — диалог и окно
  настроек. Ссылка на процесс в библиотеке обнуляется при любом `exit`, поэтому выход больше не
  виснет на мёртвом процессе. `/api/health` при лежащей базе — 503: Electron на старте ждёт
  `res.ok`, «Проверить подключение» у клиента честно покажет недоступность.
- **Упавшая миграция лечится автоматически.** На PostgreSQL `migrate deploy` атомарен
  (проверено 08.09 на клоне), поэтому `resolve --rolled-back` + один повтор безопасны. Страховка —
  копия `pgdata` в `<dataDir>-before-update` при остановленном кластере, только когда есть
  новые миграции (список применённых — в `schema-ready.json`), с запасом места 2×; нет места —
  идём без копии (атомарность + JSON-копия при прошлом выходе), старую копию при этом не трогаем.
  В сборке нет `pg_dump`, физическая копия папки — единственный способ. Правило для будущих
  миграций: без `BEGIN/COMMIT` и `CREATE INDEX CONCURRENTLY` — иначе атомарность теряется.
- **Место на диске** — предупреждаем, не блокируем: статус системы отдаёт `disk` (данные,
  копии, логи; порог `DISK_WARN_MB`), баннер красный с приоритетом над копиями, диалог при старте
  Electron < 500 МБ. Ошибка записи лога больше не роняет сервер (`logger.on('error')`),
  `uncaughtException` пишет в stderr и выходит кодом 1 — надзор Electron перезапустит.
- **Не делаем:** ICU; `trust`; автоматическое пересоздание кластера; запрет запуска при
  нехватке места; ротацию логов (D8-008, волна 2).

### Перенос на новый ноутбук — через копию на флешке, а не база на флешке (2026-09-08)
**Вопрос владельца:** вынести базу на внешний носитель, чтобы при смене ноутбука у клиента
ничего не переносить. **Решение — нет:** живой PostgreSQL на флешке изнашивает её за месяцы
(постоянная запись WAL и контрольных точек), выдернутая во время записи флешка = повреждённый
кластер, нужна NTFS, буква диска меняется между машинами, пароль базы лежит в `config.json`
профиля, а копии рядом с базой — не копии. Вместо этого:
- **Копии сами уезжают на флешку.** Папка копий задаётся в «Настройке системы» (рекомендуем
  флешку/внешний диск). Копия делается ночью в 03:00, **при старте, если последней удачной больше
  20 ч** (`BACKUP_MAX_AGE_HOURS`), **каждые 4 ч работы** (`BACKUP_EVERY_HOURS`) и **при выходе из
  программы** (Electron зовёт `POST /api/system/backup` по внутреннему токену `INTERNAL_TOKEN`,
  который живёт только в памяти процесса и принимается только с loopback). Закрывает аудит D8-003.
- **Флешки нет — копия не пропадает:** пишется в запасную папку на этом компьютере
  (`BACKUP_FALLBACK_PATH`, в Electron — `userData/backups-local`), в `BackupLog` это видно
  (`error: 'BACKUP_PATH недоступна: …'`), в программе — жёлтый баннер «Копия записана на этот
  компьютер: вставьте флешку — при выходе копия запишется на неё». Папку на несуществующем диске
  программа не создаёт. Ротация `BACKUP_KEEP` — в каждой папке отдельно.
- **Новый ноутбук:** установить программу → мастер первого запуска → после создания администратора
  шаг «Перенос данных с прошлого компьютера»: выбрать файл `backup_*.json` с флешки → сводка
  «что восстановится / что исчезнет» с той же галочкой, что в разделе копий → восстановление →
  вход прежней учётной записью (восстановленные учётки заменяют только что созданную). Тот же
  путь доступен позже: «Настройки → Резервная копия → Загрузить файл копии…»
  (`POST /api/system/backup/upload`, до 200 МБ, только SUPER_ADMIN).
- Статус копий: `GET /api/system/status.backup` (`never | stale > 48 ч | fallback | none`) — баннер
  после входа; `GET /api/system/backups.status` — блок в разделе копий (дата, путь, причина).
- **Не делаем:** база на внешнем диске; выбор папки копий из самой программы (остаётся под
  паролем сисадмина); шифрование копий (отдельный вопрос аудита D8-013).

### Многопользовательская работа = локальный сервер в одной сети (2026-06-18)
- **Модель:** один ноут — **хост** (на нём Postgres + Node-сервер), остальные ноуты —
  Electron-клиенты, обращаются к хосту по **локальной сети**. Наружу (в интернет) ничего
  не выставляется — работает только внутри LAN/Wi-Fi гостиницы. Для нашего случая это ок.
- **Почему:** это desktop-программа (не веб-сервис); общая БД нужна, чтобы оба админа
  видели одни брони. Один источник истины = одна машина с базой.
- **Что уже готово:** сервер слушает `0.0.0.0` (`server.js`), broadcast Socket.io летит
  всем клиентам (`socketManager.js`) → realtime между ноутами заработает сам.
- **Что нужно настроить (TODO ниже):** (1) на хосте — статический/закреплённый локальный IP;
  (2) клиент должен знать адрес хоста — сейчас в `client/src/api/client.ts` относительные URL
  (`/api`, `io('/')`), в упакованном Electron они ни к чему не резолвятся → нужно вынести
  base URL в конфиг (напр. `http://<IP-хоста>:3001`); (3) CORS/`CLIENT_ORIGIN` пустить
  origin клиентов; (4) брандмауэр Windows — открыть порт 3001 на хосте.
