## 1c. Разбор `move` (обе ветки) — что происходит с деньгами

**Общие проверки (`:758-799`):** статус `CHECKED_IN`; `checkIn ≤ moveDate < checkOut`; `moveDate ≤ BD`; целевой номер существует и активен; «тот же номер + `moveDate == checkIn`» → 400.

**Ветка A — день-в-день (`moveDate == checkIn`, `:807-834`).** Одна транзакция: `findRoomBlock` (пересечение → буфер → квота, `excludeBookingId = id`, метки/партнёр брони; `allowAllotmentOverride` снимает квоту) → `update { roomId }`. Ничего больше не меняется: `BookingCharge` (цена старой категории), `BookingService`, `Payment`, `paidAmount`, заметки, `actualCheckInAt` — как были. Событие `booking:updated`. Замечания: D3-010 (история/заметка), D3-011 (нет переоценки).

**Ветка B — сплит (`:841-977`).**
1. До транзакции — пропорция по ночам: `nightsFirst/nightsAll` для `totalAmount`, `prepaidAmount`, `paidAmount` (округление в первую часть, остаток — во вторую; сумма частей точно равна исходной).
2. Транзакция: `findRoomBlock` на `[moveDate, checkOut)` **без** `excludeBookingId` (тот же номер = помеха, по замыслу) → оригинал: `checkOut = moveDate`, `CHECKED_OUT`, `actualCheckOutAt = movedAt`, три суммы по пропорции, заметка «Переезд в №…» → новая бронь: `checkIn = moveDate`, `CHECKED_IN`, `actualCheckInAt` наследуется, документ/гости/скидка/предоплата-%/метки/партнёр/источник копируются, `adminId = текущий`, `shiftId = старый`, заметка «Переезд из №…» (исходные заметки **не** копируются), три суммы — остаток → `BookingService` копируется `createMany` → если у оригинала есть строки начислений: `stay`-строки с `date ≥ moveDate` переносятся `updateMany` на новую бронь; `meal`/`extra`/`discount` (все с `date: null`) остаются; `recalcBookingTotals(оригинал)` (строгий: сумма оставшихся строк, `prepaidAmount = total × %`), `recalcBookingTotals(новая, keepIfEmpty)` (если stay-строк не переехало — остаётся пропорция) → если строк нет вообще (старые 107 броней) — остаётся только пропорция из п. 1.
3. `Payment` не трогаются вовсе — все остаются на оригинале; `recalcBookingPaid` не вызывается. Итог: `paidAmount` обеих частей — доли пропорции, «принято» по журналу — 100 % на оригинале, 0 на новой (D3-001).
4. События: `booking:updated` (оригинал) + `booking:created` (новая); один авто-снимок.

Инварианты, которые держатся: Σ `totalAmount` частей = исходному при наличии строк (строки только перекладываются) и без строк (пропорция); Σ `paidAmount` = исходному до первой операции с платежом. Инварианты, которые не держатся: «`paidAmount` = Σ `Payment` брони» (D3-001), «итог части = стоимость её ночей» (D3-002), «питание начислено один раз» после пересборки второй части (D3-002), неотрицательность итога (D3-002).

## 2. Что в порядке

- `bookingController.js:findRoomBlock/respondRoomBlocked/respondMoveBlocked` — единая проверка через `checkRoomsAvailability`; `allowAllotmentOverride` снимает только `allotment`; формы 409 (`conflict` / `code: ALLOTMENT_CONFLICT` / текст буфера) сохранены.
- `bookingController.js:create` — минимум 1 ночь; бэкдейтинг только ремонту; `CHECKED_IN` в будущее/ремонту принудительно `CONFIRMED`; номер активен; услуги существуют; смена определяется до транзакции; бронь + услуги + начисления в одной транзакции; `keepIfEmpty` не обнуляет ручную сумму; событие после коммита.
- `bookingController.js:update` — `CHECKED_OUT`/`CANCELLED` заблокированы целиком; у заселённого `checkIn` и `roomId` фиксированы, `checkOut` только > BD; новый номер проверяется на активность; бэкдейтинг заезда закрыт; проверка свободности с `excludeBookingId` и итоговыми метками; пересборка строк только при изменении входов (`chargeInputsChanged` + `serviceLinksChanged` + `recalcCharges`); частичный PUT не стирает документ и услуги; STAFF не может править фактические времена (403).
- `bookingController.js:cancel` — отмена, не удаление; повторная отмена и отмена закрытой → 400; заселённого отменяет только ADMIN+.
- `bookingController.js:checkIn` — только `CONFIRMED`, не ремонт, не раньше даты заезда по смене; `actualCheckInAt = now`.
- `bookingController.js:checkOut` — только `CHECKED_IN`; рабочая дата раньше заезда → 400 (закрывает июньский «`checkOut < checkIn`»); день-в-день → `CANCELLED`, не delete; ранний выезд фиксирует `checkOut = BD`, `actualCheckOutAt = now`.
- `bookingController.js:move` — обе ветки в транзакции; `moveDate` не позже смены; деактивированный целевой номер → 404; метки/партнёр/документ/услуги едут с гостем; `adminId` (не `createdById`); отказ возвращается из транзакции, чтобы не потерять `code`.
- `bookingController.js:checkAvailability` — то же правило, что сохранение; пустой период отвечает 200 с `reason: 'range'`; `conflict` только для пересечения (квота не блокирует кнопку).
- `bookingController.js:*Charge` — причина обязательна; правка автостроки делает её ручной; скидка не может быть плюсом; пересчёт итога в той же транзакции; отменённой брони строки не правятся; `chargeId` сверяется с `bookingId`.
- `utils/availability.js:checkRoomsAvailability` — один запрос броней окном `± maxBuf`, `excludeBookingId`, полуоткрытые интервалы, порядок «пересечение → буфер → квота»; квоты только для ещё свободных.

## 6. Вопросы владельцу (тяжесть 4)

1. **Ранний выезд** (D3-005): политика — берём за фактические ночи (тогда `checkout` должен пересобирать/помечать строки) или за весь срок (тогда договориться, что `roomNights` ≠ `charges`, и написать это в решениях)?
2. **Поздний заезд**: гость приехал через 2 дня после даты заезда — ночи до приезда остаются в счёте и в занятости номера. Так и надо (no-show-ночи платные) или дату заезда сдвигать?
3. **Незаезд** (D3-006): нужен ли статус `NO_SHOW` как переход — кнопкой «Не приехал» и/или автоматически при «Следующем дне» для `CONFIRMED` с прошедшим заездом? Пока единственный путь — «Удалить», и метрика «Доля незаездов» мертва.
4. **Партнёрские брони** (D3-003): нужна ли вообще «бронь партнёра» (поле партнёра в форме), или квоты — это только «предупредить при продаже»? Во втором случае подтверждение при каждом сохранении брони в квотном номере — ошибка, которую надо убирать.
5. **Переезд и деньги** (D3-001/002): при сплите — переносить ли платежи/строки питания на вторую часть пропорционально ночам, или деньги всегда остаются на «первой» брони, а вторая — бесплатное продолжение (тогда её долг должен быть 0 по определению)?
6. **Переселение в другую категорию** (D3-011): апгрейд по вине отеля — бесплатно, по желанию гостя — по новой цене? Сейчас ответ зависит от того, какой кнопкой воспользовались.
7. **Откат смены** (D3-013): нужна ли штатная «отмена перехода дня» для случая двойного нажатия, или достаточно инструкции «править в базе»?
8. **Скрытые метки** (`hiddenFlagCodes` — клиентский список): сервер не знает о скрытии, эффекты скрытой метки на старых бронях продолжают действовать (буфер, pin). Это ожидаемо?
9. **Оптимизатор и квоты** (D3-007): квотные номера — исключить из перестановок целиком или разрешать ходы только внутри партнёра?
10. **Бэктест** (D3-021): чтобы получить денежную оценку, нужно либо заполнить цены тестовым 94 броням (они без строк начислений), либо принять, что бэктест — только «в ночах». Что выбираем до показа зимой?
