## Подробности

### S13-001 🟠 Срок брони не ограничен сверху

`controllers/bookingController.js:364` проверяет только `checkOut > checkIn` и «не в прошлом».
Верхней границы нет ни в валидаторах (`routes/bookings.js:86` — `body('checkOut').isDate()`),
ни в контроллере. Генератор строк при этом посуточный:

```js
// utils/charges.js:32
function nightsOf(checkIn, checkOut) {
  const out = []
  for (let t = from; t < to; t += DAY) out.push(new Date(t))
  return out
}
```

- **Воспроизведение:** `POST /api/bookings {roomId, guestName, checkIn:"2026-07-10", checkOut:"2126-07-10"}`
  → 201, в базе бронь на **36 524 ночи**. При заполненном календаре цен это столько же строк
  `BookingCharge` в одной транзакции; при незаполненном — столько же объектов в памяти и в
  `missingPrices` (S13-003). Реальный вход — не атака, а опечатка в году на стойке
  («2926» вместо «2026»): поле даты в форме её пропускает.
- **Ожидалось:** 400, как у тарифов — там граница уже есть и подписана словами
  «Больше двух лет за один заход — почти наверняка опечатка в датах»
  (`rateController.js:5`, `MAX_RANGE_DAYS = 800`).
- **Правка (1 строка):** в `create`/`update` рядом с проверкой `checkOut > checkIn` добавить
  `if (nightsOf(checkIn, checkOut).length > MAX_NIGHTS) return next(createError('Слишком длинный срок брони', 400))`
  с общей константой (напр. 400 ночей) и то же условие в `preview`.
- **Тест:** `audit13-server-limits.test.js` → «S13-001 · длина брони».

### S13-002 🟠 200 МБ тела читаются до проверки токена

```js
// src/app.js:51 — ДО app.use(maintenanceGate) и до любого роутера с authenticate
app.use('/api/system/backup/upload', express.json({ limit: '200mb', type: () => true }))
```

Сам роут закрыт правильно (`routes/system.js:120`, `requireRole('SUPER_ADMIN')`), но
`authenticate` живёт внутри роутера, то есть **после** парсера. `apiLimiter` подключён там же,
в `app.use('/api/system', apiLimiter, systemRoutes)` — то есть тоже после.

- **Воспроизведение:** `POST http://<хост>:4780/api/system/backup/upload` без заголовка
  `Authorization`, тело — 3 МБ битого JSON. Ответ — **400 «Это не файл резервной копии
  Roomline PMS»**, а не 401: тело прочитано и разобрано. С телом в 200 МБ `JSON.parse`
  съедает несколько сотен мегабайт; повторить с любого ноутбука в гостиничном вайфае можно
  сколько угодно раз подряд.
- **Насколько опасно:** это не кража данных, а способ погасить сервер отеля с чужого
  устройства в той же сети. Надзор Electron поднимет сервер заново, но стойка на это время
  встанет. Модель угроз у продукта мягкая («свои в своей сети»), поэтому 🟠, а не 🔴.
- **Правка (1–2 строки):** перед парсером на этом пути поставить `authenticate` (и
  `requireRole('SUPER_ADMIN')`): `app.use('/api/system/backup/upload', authenticate, requireRole(...), express.json({limit:'200mb', …}))`.
- **Тест:** `audit13-server-http.test.js` → «S13-002».

### S13-004 🟠 Замок версии брони не атомарен

```js
// controllers/bookingController.js:499 — проверка ВНЕ транзакции
if (isStale(req.body.expectedUpdatedAt, existing.updatedAt)) { … 409 BOOKING_STALE }
…
// :631 — запись, where без версии
const updated = await tx.booking.update({ where: { id }, data: { … } })
```

- **Воспроизведение:** два рабочих места открыли бронь №12 с одним и тем же `updatedAt`.
  Обе формы сохраняются в пределах одного-двух десятков миллисекунд: оба запроса проходят
  `isStale` (в базе ещё старая версия), оба доходят до `update` — 409 не будет ни у кого,
  правка первого исчезнет молча. Ровно тот сценарий, ради которого замок и делали (D5-004).
- **Ожидалось:** сравнение версии и запись — одна операция.
- **Правка (2 строки):** внутри транзакции вместо `tx.booking.update({where:{id}})` —
  `const {count} = await tx.booking.updateMany({ where: { id, updatedAt: expected }, data })`
  и `if (count === 0) throw stale()`. `expectedUpdatedAt` не прислали — ветка прежняя.
- **Тест:** `audit13-server-limits.test.js` → «S13-004», проверка идёт по самому запросу
  (в `where` нет `updatedAt`).

### S13-006 🟠 Лимитер входа считает и проверку сессии

```js
// src/app.js:75-94
const authLimiter = rateLimit({ windowMs: 15*60*1000, max: NODE_ENV==='production' ? 20 : 500, … })
app.use('/api/auth', authLimiter, authRoutes)
```

Под лимитером весь `/api/auth/*`, включая `GET /auth/me` — его клиент зовёт при каждом старте
приложения и после каждого восстановления сессии.

- **Воспроизведение (тест, NODE_ENV=production):** 20 запросов `GET /api/auth/me` → следующий
  `POST /api/auth/login` отвечает **429 «Слишком много попыток входа. Попробуйте через 15 минут.»**
  На стойке это выглядит как «программа не пускает», причём чем активнее человек перезапускает
  программу, пытаясь починить, тем надёжнее он себя запирает. Складывается с S13-007: неверный
  регистр логина жжёт тот же лимит.
- **Правка (1 строка):** повесить `authLimiter` точечно на `/login` (и `/change-password`),
  а не на весь роутер: `router.post('/login', authLimiter, loginRules, validate, login)`.
- **Тест:** `audit13-server-http.test.js` → «S13-006».

### S13-008 🟠 Лицензия не привязана к объекту

Шапка `utils/license.js:10-13` обещает: «Ключ привязан к НАЗВАНИЮ объекта: скопировать его
соседней базе отдыха технически можно, но там будет чужое название в шапке программы».
В коде этой связи нет ни одной строки: `evaluateLicense` (`:292`) проверяет только подпись и
дату сборки, `licenseController.activate` (`:43`) записывает ключ, не заглядывая в
`HotelSettings.name`, а шапка программы берёт имя из настроек, а не из ключа — то есть
«чужое название» никогда и не появится.

- **Воспроизведение:** ключ, выписанный для «Туран», активируется на базе с `name = "Дорожник"`
  → `state: 'ok'`, лимит номеров 45, пробный период отменён. Ни отказа, ни предупреждения.
- **Насколько опасно:** данным клиента ничего не грозит; страдает единственный коммерческий
  рычаг — один купленный ключ обслуживает сколько угодно объектов.
- **Правка (1–2 строки):** в `buildResponse` сравнить `payload.hotel` c `HotelSettings.name`
  (без регистра и лишних пробелов) и вернуть `hotelMismatch: true`; при активации — отказ
  либо подтверждение «ключ выписан другому объекту».
- **Тест:** `audit13-server-limits.test.js` → «S13-008».

### S13-010 🟠 Правка заселённой брони переоценивает прожитые ночи

```js
// controllers/bookingController.js:682-687
await rebuildChainCharges(accountId, {
  …, frozenBefore: existing.accountBookingId ? existing.checkIn : null,
})
```

Заморозка прожитых ночей включается **только у продолжения цепочки**. У обычной брони
`frozenBefore = null`, и `rebuildChainCharges` сносит все авто-строки и считает их заново по
сегодняшнему календарю цен — включая ночи, которые гость уже прожил. Ранний выезд
(`planEarlyCheckout`) и переезд (`move`) от этого защищены, обычный `PUT` — нет.

- **Воспроизведение:** гость живёт с 8 июля (5 ночей по 40 000, строки на месте), рабочая дата
  10 июля. 5 июля в календарь внесли новую цену — 45 000. На стойке 10-го подселяют третьего
  взрослого (`PUT /bookings/:id {adultsWithMeals: 3}`). Ночи 8 и 9 июля **пересчитываются по
  новому календарю**: счёт за уже прожитое молча вырос.
- **Ожидалось:** прожитые ночи не переоцениваются никогда — это правило проекта, оно
  выписано в `planEarlyCheckout` и в `rebuildChainCharges`.
- **Правка (1 строка):** `frozenBefore: existing.status === 'CHECKED_IN' ? businessDate : (existing.accountBookingId ? existing.checkIn : null)`.
- **Тест:** `audit13-server-limits.test.js` → «S13-010». Пункт известен: он записан
  наблюдением волны 5a в `NOTES.md` («обычный PUT по заселённой брони переоценивает все ночи»)
  и с тех пор не закрывался.

### S13-011 🟠 Переменные окружения снимают лицензию и заслонку 1.0

`electron/main.js:706` собирает окружение сервера как `{ ...process.env, … }`, то есть
**всё пользовательское окружение Windows наследуется**. А в сервере есть три обхода,
рассчитанных на «только для тестов»:

| Переменная | Что делает | Где |
|---|---|---|
| `ROOMLINE_TRIAL_DAYS` | длина пробного периода, любое целое | `utils/trial.js:31` |
| `ROOMLINE_BUILD_DATE` / `QONAQ_BUILD_DATE` | дата сборки для гейта обслуживания | `utils/license.js:272` |
| `FEATURE_PREVIEW` | включает спрятанные из 1.0 оптимизатор и **откат к снимкам** | `utils/features.js:89` |

Комментарий в `trial.js:21` прямо утверждает «В установленной программе переменной нет» —
это неверно: переменная уровня пользователя ставится без прав администратора и подхватывается
при следующем запуске.

- **Воспроизведение:** `setx ROOMLINE_TRIAL_DAYS 3650` → перезапуск программы → пробный период
  вечен. `setx FEATURE_PREVIEW 1` → в API оживает `POST /api/snapshots/:id/restore`, то есть
  откат всей базы, спрятанный владельцем именно потому, что «до доработки это опаснее, чем полезно».
- **Правка (1–2 строки):** читать эти переменные только когда `process.env.NODE_ENV !== 'production'`
  (упакованный сервер стартует с `NODE_ENV=production`, `electron/main.js:714`).

### S13-012 🟠 Последний день квоты партнёра продаётся молча

```js
// utils/allotment.js:47-48
const overlapFrom = Math.max(toUTC(a.dateFrom).getTime(), from.getTime())
const overlapTo   = Math.min(toUTC(a.dateTo).getTime(),   to.getTime())
```

Период квоты полуоткрытый: `dateTo` **не входит**. Форма при этом подписана «С даты» / «По дату»
(`client/src/components/Settings/sections/AllotmentsSection.tsx:216-231`), а текст отказа
печатает обе даты подряд — «Номер выделен партнёру «X» на 01.07.2026 — 10.07.2026»
(`utils/allotment.js:106`), что читается как «включительно».

- **Воспроизведение:** квота на №12 с 01.07 по 10.07. Бронь №12 на 10–12 июля сохраняется
  **без вопроса про квоту**, хотя менеджер считает, что 10-е за партнёром.
- **Насколько опасно:** ночь, за которую партнёр заплатил, уходит стороннему гостю; узнают
  об этом на заезде. Один день — но именно тот, что на стыке.
- **Правка (решение владельца, 1 строка в любом случае):** либо записывать `dateTo + 1 день`
  при сохранении квоты, либо переименовать поле в «По дату (не включая)» и так же
  печатать в сообщении. Тест не писал намеренно: выбор семантики — не дело аудита.

### S13-016 🟠 Отмена платежа меняет закрытую кассу задним числом

`paymentController.voidPayment` (`:474`) не смотрит, к какой смене относится платёж: строка
получает `voidedAt`, а `shiftId` у неё остаётся прежним. Отчёт по смене считает итоги
по строкам на лету (`shiftSummary:118`), поэтому цифры **вчерашней, уже сданной смены**
меняются в тот момент, когда сегодняшний администратор нажимает «Отменить запись».

- **Воспроизведение:** вчера приняли 50 000 наличными, смену закрыли и сдали деньги. Сегодня
  запись отменяют с причиной «не та бронь» → вчерашний `byMethod.cash.received` стал 0,
  а `net` — минус. Касса вчерашнего дня больше не сходится с тем, что сдали.
- **Смягчающее:** отменённые видны отдельной строкой (`voidedCount`, `voidedAmount`), то есть
  след остаётся; но подписи «принято за смену» это не чинит.
- **Правка (1–2 строки):** отменять можно только платёж текущей смены; для чужой смены —
  400 с текстом «смена закрыта, проведите возврат» (возврат ложится в сегодняшнюю смену
  и кассу прошлого дня не трогает).

### S13-003 🟡 Предпросмотр отдаёт запись на каждую ночь без цены

`utils/charges.js:194` — `missingPrices.push({date, parts})` на каждую ночь, у которой не

## Что выглядит надёжно

- **Двойная продажа номера.** `utils/availability.js` — единственное определение «свободно»
  (пересечение → буфер метки → квота), даты полуоткрытые, окно запроса шире периода ровно на

  «Начислено/принято/долг» живут в одном модуле (`bookingMoney.js`) и не продублированы в

  документа нет вовсе (проверено грепом по `reports/`).
- **Мастер первого запуска.** Единственный публичный записывающий путь закрыт составом учёток,

  порядок middleware; проверить, что `body('checkIn').isDate()` отвергает «2026-13-45»,
  без поднятия роутера нечем. **Это замечание к архитектуре тестов, а не к коду.**
- **Настоящие гонки** (два одновременных `PUT`, два платежа, два `next-day`) на фейковой
  Prisma не воспроизводятся: у неё нет изоляции транзакций. S13-004 и S13-017 доказаны по
  запросу (`where` без версии) и по коду, а не по столкновению.
- **Всё, что требует живой базы:** exclusion-constraint, поведение `$transaction` при
  конфликте, реальный размер ответа `preview` на опечатке в веке, восстановление копии.
  К базе не подключался по условию задачи.
- **`utils/backup.js` и `utils/snapshot.js`** прочитаны фрагментами (восстановление,
  расписание, гейт потери денег) — это область направления «эксплуатация», а не серверной логики.
