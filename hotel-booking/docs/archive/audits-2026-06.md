### 🔒 Аудит безопасности (2026-06-18) — что нашли в backend
Полный проход по auth/JWT/валидации/инъекциям/секретам. По убыванию критичности:

- [ ] **🔴 КРИТ. Слабый угадываемый `JWT_SECRET`.** `server/.env:11` =
      `hotel-booking-secret-key-minimum-32-chars-long` — это не случайная строка, а
      предсказуемый шаблон. Кто узнает/подберёт → подпишет свой JWT с `role:SUPER_ADMIN`
      → полный захват без пароля. В коде фоллбэка нет (ок), но значение надо заменить.
      **Фикс:** `node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"`
      → вставить в `.env`. Все текущие токены инвалидируются (перелогин) — это норм.
- [ ] **🔴 КРИТ. Дефолтный пароль БД `postgres:password`** (`server/.env:1`). При LAN-хосте
      (см. план многопользовательской работы) хост доступен по сети → слабый пароль
      Postgres = реальный риск. **Фикс:** сменить пароль роли + обновить `DATABASE_URL`.
- [ ] **🔴 КРИТ. Дефолтные креды админа `admin / admin123`** (`server/prisma/seed.js:65`).
      Если на боевой не сменили — вход одной строкой. **Фикс:** сменить пароль после
      первого запуска; в идеале форсить смену при первом входе.
- [x] **✅ ИСПРАВЛЕНО (2026-09-04). Парольная политика поднята и сведена в один источник.**
      Было: 6 символов в `routes/auth.js`, 8 в `routes/users.js` и `routes/setup.js`,
      8 на клиенте — три разных правила. Стало: **≥10 символов, минимум одна буква и
      одна цифра, без пробелов по краям, ≤72 (предел bcrypt)**. Источник правды —
      `server/src/utils/passwordPolicy.js` (его `passwordRule` подключён в `auth.js`,
      `users.js`, `setup.js`), зеркало на клиенте — `client/src/components/Setup/accountRules.ts`
      (тексты совпадают дословно; правку делать в обоих файлах).
      Ошибка перечисляет ИМЕННО то, что не так: «Пароль не подходит: нужно не менее
      10 символов (сейчас 6); нет ни одной цифры».
      **Важно:** правило применяется только при ЗАДАНИИ пароля (смена, создание,
      сброс, мастер первого запуска) и НЕ применяется при входе — учётные записи со
      старыми короткими паролями продолжают входить (проверено).
- [ ] **🟡 `exec()` со строковой склейкой в бэкапе** (`server/src/utils/backup.js:26`).
      Параметры из `DATABASE_URL` (env, не польз. ввод) → не прямая инъекция, но
      спецсимволы в пароле сломают команду/утекут в shell. **Фикс:** `execFile('pg_dump', [...])`
      без shell.
- [ ] **🟡 JWT нельзя отозвать** — `logout` чисто клиентский (`authController.js:37`).
      Украденный токен живёт до 8 ч. Для desktop/LAN приемлемо, держим в уме.
- [ ] **🟡 CORS в проде** (`server/src/app.js:28`): при незаданном `CLIENT_ORIGIN` дефолт на
      localhost. Для LAN-хоста явно задать origin клиентов (пересекается с TODO про общую БД).

**Что ОК (для памяти, чтобы не перепроверять):** helmet, rate-limit на /api/auth (20/15мин
в проде) и общий API-лимит; логин не различает «нет юзера»/«неверный пароль» (нет
user-enumeration); bcrypt cost 12, пароли не уходят клиенту; errorHandler не отдаёт
стек/детали 500; все API-роуты и Socket.io под `authenticate`, мутации фонда/бэкапов под
`requireRole`; `$executeRawUnsafe` в snapshot.js — статическая строка (инъекции нет);
`.env` не закоммичен (в git только `.env.example`). Race condition двойного бронирования —
отдельным пунктом ниже (был №1 ещё до аудита).

### 🧮 Аудит бизнес-логики броней (2026-06-18) — переходы статусов vs смена
Проход по `bookingController.js`: даты/смена vs статусы. Суть: переходы статусов и
прямой статус при создании НЕ сверяются с бизнес-датой (датой смены). Общее правило-фикс:
**CHECKED_IN допустим только когда `businessDate >= booking.checkIn`** + единый запрет
прошлых дат в `create` И `update`. На текущих (тестовых) данных живых случаев нет, но код
их пропускает.

- [x] **✅ ИСПРАВЛЕНО (2026-06-18). `checkIn` сверяется со сменой** (`bookingController.js`).
      Добавлена проверка `businessDate < checkInUTC` → нельзя отметить «заехал» раньше даты
      заезда брони (поздний заезд оставлен). Требует рестарт сервера.
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). `create` не создаёт «заехавшим» на будущее**
      (`bookingController.js`). Если дата заезда впереди смены (или это ремонт) — статус
      принудительно сбрасывается в `CONFIRMED`. Требует рестарт сервера.
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). Бэкдейтинг в `update` закрыт** (`bookingController.js`).
      Перенос заезда на дату < смены отклоняется (как в `create`); ремонт по-прежнему можно
      задним числом. Требует рестарт сервера.
- [ ] **🟠 `checkOut` может выдать бронь с `checkOut < checkIn`** (`bookingController.js:371`).
      Если бронь отметили «заехал» рано (баг выше) и сразу выезд: `todayUTC < checkOut` →
      ставит `checkOut = todayUTC` < `checkIn` → невалидная бронь. Корень — баг №1, но `checkOut`
      стоит защитить отдельно.
- [ ] **🟠 `checkOut` день-в-день молча УДАЛЯЕТ бронь физически** (`bookingController.js:363`).
      `prisma.booking.delete` — реальное удаление из БД, тогда как `cancel` принципиально не
      удаляет (стр. 291). Потеря записи/истории/аудита. **Фикс:** ставить `CANCELLED`, а не delete.
- [ ] **🟡 `move` — проверка пересечений вне транзакции** (`bookingController.js:447`): `findOverlap`
      идёт ДО `$transaction`, а same-day-ветка (стр. 426) вообще без транзакции → тот же класс
      race condition, что и в `create`.
- [ ] **🟡 `move` сплит обнуляет деньги на новой брони** (`bookingController.js:490`):
      `totalAmount/prepaidAmount/paidAmount = 0` → оплата «теряется» на переехавшей части.
      Всплывёт, когда начнём заполнять цены (см. TODO про цены).
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). «Ремонт» нельзя отметить «заехал»** (`bookingController.js`):
      `checkIn` теперь отклоняет брони с `source==='ремонт'`. Требует рестарт сервера.

- [x] **✅ ИСПРАВЛЕНО (2026-06-18). Двойное бронирование (race condition) — был ПРИОРИТЕТ №1.**
      В БД добавлен **exclusion-constraint** `booking_no_overlap`:
      `EXCLUDE USING gist (roomId WITH =, daterange(checkIn,checkOut) WITH &&) WHERE status
      IN ('CONFIRMED','CHECKED_IN')` + `CREATE EXTENSION btree_gist`. Теперь БД **физически
      запрещает** пересечение активных броней — даже при одновременном сохранении двумя
      админами второй INSERT/UPDATE отклоняется. `errorHandler.js` ловит нарушение и отдаёт
      дружелюбный 409. Транзакции НЕ понадобились — constraint и есть гарантия.
      - SQL: `server/prisma/sql/booking_no_overlap.sql` (применён напрямую через
        `npx prisma db execute`, т.к. проект на `db push`, миграций нет).
      - Перед применением проверено: существующих пересечений в базе не было.
      - **Откат:** `ALTER TABLE "Booking" DROP CONSTRAINT booking_no_overlap;`
      - Код errorHandler требует рестарт сервера; constraint уже активен в БД.
- [ ] **Совместная работа двух ноутов = нужна одна общая БД-машина.** (2026-06-18)
      Это desktop-программа (Electron), web-режим — только для разработки, чтобы не
      пересобирать exe. Значит каждый ноут со своим локальным Postgres = **отдельные базы**,
      броней друг друга не видят. Для совместной работы один ПК/ноут хостит Postgres + Node,
      остальные Electron-клиенты подключаются к нему по локальной сети (`DATABASE_URL` и
      адрес API указывают на IP сервера). Код к этому готов: `HOST=0.0.0.0`, относительные
      URL в `client/src/api/client.ts`, broadcast в `socketManager.js` (realtime между
      клиентами уже рассылается всем). Топология **выбрана** — LAN-хост (см. «Принятые
      решения»). Осталось реализовать: base URL клиента в конфиг, CORS/`CLIENT_ORIGIN`,
      статический IP хоста, открыть порт 3001 в брандмауэре.
- [ ] **Оптимизатор на боевых данных.** Текущий бэктест — на разреженных данных
      (загрузка 16.7%, без цен) → эффект занижен. Прогнать на плотном сезоне с ценами.
      Скрипт: `server/scripts/optimizer-backtest.js` (READ-ONLY).
- [ ] **Перенос кастомных меток из localStorage в БД.** Если были свои метки в браузере,
      в БД их нет (там 3 дефолта). Сделать разовый перенос при необходимости.
- [ ] **Особенности/вместимость/корпуса всё ещё в localStorage** (не в БД). Для продакшена
      тоже стоит поднять в БД (как сделали с метками), чтобы соблюдались везде.
