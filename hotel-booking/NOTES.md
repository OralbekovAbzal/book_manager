## 🟢 Активные идеи / направления (что делать дальше)

### Справочник → вкладка «Гости» (2026-09-02)
**Идея:** собрать адресную книгу постояльцев из уже существующих броней — заводить
руками ничего не надо, данные копятся сами.
- **Что показывать:** карточка гостя = имя, телефон, сколько раз жил, всего ночей,
  последний визит + список его броней с переходом к ним в шахматке.
- **Ключ группировки — телефон, а не имя.** Имя пишут по-разному («Асель»,
  «Асель К.», «Асель Каримова»), номер один. По имени склеятся разные люди.
- **Что вылезет на живых данных:** номера записаны как попало (`+7 701…`, `8701…`,
  со скобками и пробелами) — для базы это разные строки, нужна нормализация при
  сравнении, иначе один гость размножится на несколько карточек.
- **Брони без телефона** (поле необязательное) в список не попадут. Показать их
  отдельной кучкой честнее, чем группировать по имени и соврать.
- **Зачем:** решает реальную боль стойки — «звонит гость, бронировал на июль».
  Сейчас найти его можно только листая шахматку. Плюс «постоянный гость, дайте скидку».
- **Оценка:** ~полдня, если не считать возню с нормализацией телефонов.

### Пресет контактов на свежей установке (2026-09-02)
Справочник на новой установке пустой → на демо выглядит недоделанным. Засеять то,
что одинаково у всех: 103 / 101 / 102, аварийная газовая, горводоканал, электросети.
Клиент открывает — там уже осмысленный список, остаётся дописать своего сантехника.
Та же логика «пресеты вместо настройки», что и с метками броней (см. ниже).

### Пресеты особенностей и меток (главное направление по оптимизатору)
**Идея (твоя):** не заставлять пользователя настраивать эффект каждой метки/особенности.
Вместо этого — заранее сделать **большую готовую библиотеку** особенностей и меток
с уже прописанными эффектами. Пользователь просто **скрывает ненужные** и пользуется
нужными. Мы один раз продумываем словарь и пресеты — клиент только вкл/выкл.
- **Почему важно:** сам алгоритм — простая часть, сложное — настройка под каждую базу.
  Пресеты снимают эту сложность для нетех-пользователя.
- **Что уже готово под это:** метки с эффектами хранятся в БД (`BookingFlag`),
  движок понимает словарь эффектов (буфер до/после, «не перемещать»).
- **Что осталось:** наполнить библиотеку пресетов; заменить «удалить» на «скрыть/показать»
  (поле `hidden`/`isActive` у метки и особенности); продумать список стандартных
  особенностей (типы кроватей, балкон, вид, этаж- only и т.д.) с эффектами по умолчанию.

### Путь оптимизатора во «флагман» (по убыванию ценности)
1. **Подбор под запрос** 🥇 — «есть на 5 ночей с 3 июля?»: мгновенный ответ + если не
   помещается, предложить микро-перестановку неподтверждённых броней. Превращает
   оптимизатор из пассивного в инструмент продаж (ловит брони, которые иначе теряются).
2. **Счётчик потерянной выручки** — «за месяц отвернули N запросов = X тенге». Нужен
   мини-журнал отказов.
3. **Подсказка при заведении брони** — класть новую бронь сразу оптимально (профилактика
   фрагментации вместо лечения).
4. **Цель = выручка, а не окна** — взвешивать окна по цене/сезону (yield management).
5. **Автопилот** — система сама держит сетку чистой, сигналит только при реальной выгоде.

### Расширение словаря эффектов меток
Те же «кубики», добавляются по одному (обработчик в движке + поле в форме метки):
- **Только этажи […]**, **Только корпуса […]**, **Требует особенность […]**.
- Каркас готов: `optimizeController.js` (буферы/pin) + `utils/flagEffects.js`.

## ✅ Принятые решения (что и почему сделано так)

### Язык формул в отчётах + готовые показатели + «спросить у пользователя» (2026-09-03)
**Откуда.** Первая версия конструктора умела только «поле» и «агрегат по полю».
Отзыв после пробы: «формулы из нескольких данных не сделать, даже процент
загруженности не собрал, и непонятно, как настроить, что пользователь вводит».
Все три претензии — одна причина: нет выражений.

**Решение — свой язык формул (`server/src/reports/expr.js`), без `eval`.**
Формула приходит из конструктора или чужого JSON, поэтому у неё нет доступа ни к
чему, кроме арифметики над строкой: свой токенизатор → разбор с приоритетами →
вычислитель по дереву. Имена = поля источника, ключи колонок ВЫШЕ по списку,
`@ключ` — параметры. Агрегаты `sum/count/countIf/sumIf/avg/countDistinct/minOf/
maxOf/first` считают по строкам группы; внутри агрегата — поля строки. Скаляры:
`round/if/coalesce/min/max/abs/concat/contains/has/days/year/month/weekday…`.
`null` в арифметике → `null`, деление на ноль → `null`, `=` сравнивает «по смыслу»
(«2» = 2). Формула работает и в колонках, и в фильтрах (`expr` = условие строки).

**Готовые показатели (`metrics` у датасета).** «Загрузка, %» = именованная формула
`sum(isSold) / sum(isAvailable) * 100` с типом и подписью — в конструкторе один клик,
режим «Показатель». Встроенная «Загрузка» переписана на показатели: это и есть
образец для тех, кто делает копию. Свои формулы — режим «Формула» с палитрой
(поля, колонки выше, параметры, функции вставляются в курсор).

**Валидация до запуска.** `analyze()` возвращает имена, параметры и ошибки формулы;
`validateDefinition` проверяет: имена известны (поля или колонки ВЫШЕ — порядок
колонок = порядок счёта), параметры объявлены, агрегаты не вложены и не стоят в
условиях фильтра, число аргументов функций. Опечатка в поле — ошибка в конструкторе,
а не молчаливый `null` в готовом отчёте. Ошибка формулы во время счёта — 400, не 500.

**Тип колонки-формулы угадывается по корню дерева** (`inferType`): строка/`concat`/
`if` с текстовыми ветками → текст, сравнения → да/нет, иначе число. Иначе
`if(nights >= 7, 'долгий', 'короткий')` получал тип «число» и «Итого: 0».
Итог плоской формулы суммируется только если все значения — числа.

**«Спросить у пользователя».** В фильтре по полю третий источник значения: параметр
создаётся сам — с типом и справочником поля (`options`/`optionsFrom` в описании
поля: корпус → список корпусов, статус → список статусов, этаж → числа). Для
свободного текста операция «одно из» без списка бессмысленна → заменяется на
«содержит». В «Параметрах» у каждого видно, где он используется; «нигде» подсвечено.
Секции конструктора теперь все раскрыты: свёрнутые «Параметры»/«Фильтры» просто не
находили.

**Проверено в интерфейсе (2026-09-03, учётка `claude`):** «Загрузка по дням» собрана
из группировки + показателя + формулы, «Спросить у пользователя» создал параметр
«Корпус» со справочником, предпросмотр по КОРПУС A дал 3,5 %; сохранение, правка,
копия встроенного, удаление — работают.

**Гочи.** Формула видит только колонки выше себя — переставили колонку, проверьте
формулы. `count()` без аргумента — строки группы, `count(x)` — непустые `x`.
Фильтр по полю с ПУСТОЙ константой не применяется (только что добавленный фильтр
не должен обнулять предпросмотр); «поле равно пустой строке» так не выразить —
используйте «заполнено» с «НЕ».
Служебные поля `isSold/isAvailable/…` (0/1) показаны в палитре моноширинно —
они существуют ради `sum()`. Добавил функцию в `expr.js` → добавь в `FUNCTIONS`
там же и в `ARITY`, иначе конструктор её не покажет / валидация не проверит.

### Конструктор и редактор отчётов + импорт JSON (2026-09-03)
Продолжение записи ниже («отчёт — это данные»): раз определение — JSON, конструктор
— это форма над ним, а не отдельная подсистема.

**Хранение.** Таблица `ReportDefinition` (`key` = строковый id из URL, `definition` JSONB).
Встроенные отчёты остаются файлами в `server/src/reports/definitions/` и в БД
не дублируются: они `source: 'builtin'`, не правятся и не удаляются — только
**копируются** (кнопка «Копия» открывает конструктор с копией как новым отчётом).
Так обновление приложения не затирает правки клиента, а клиент не ломает поставку.

**Одна валидация на всех.** `validateDefinition()` в `registry.js` возвращает СПИСОК
проблем человеческим языком (не первую попавшуюся) — его показывают и конструктор
(живой предпросмотр), и импорт, и сохранение. Правила «что можно» живут только на
сервере; конструктор физически не может собрать то, что движок не примет.

**Живой предпросмотр = `POST /reports/preview`.** Определение уходит на сервер как есть,
без сохранения; `POST /reports/validate` заодно возвращает определение с подставленными
справочниками (корпуса, категории…) для формы параметров. Дебаунс 600 мс.

**Словарь конструктора — с сервера** (`GET /reports/meta`: датасеты с полями,
операции, агрегаты, типы, справочники, пресеты, всё с подписями). Добавил операцию
в `engine.js` → добавь подпись в `vocab.js`, иначе конструктор её не покажет.

**Импорт.** `POST /reports/import`: занятый ключ — не ошибка, берётся `key-2` и
пользователю сообщается. Смысл импорта — «сложный отчёт под заказчика проще
сгенерировать снаружи (в т.ч. попросить у ИИ) и загрузить файлом». В редакторе есть
вкладка JSON (применить / скопировать / скачать / загрузить) — тот же объект.

**Права.** Создавать, править, удалять, импортировать — `ADMIN` и `SUPER_ADMIN`
(`requireRole` в `routes/reports.js`); смотреть и выгружать — все. Настройка доступа
к каждому отчёту по отдельности — следующий шаг, поле под неё в определении не заводили.

**Что попутно поправлено в движке.**
- `eq/in/...` сравнивают «по смыслу» (`String(a) === String(b)`): параметр из формы —
  строка «2», поле «этаж» — число 2; строгое `===` молча возвращало пустоту.
- Расчётные колонки без группировки = **сводка** в одну строку (сколько всего броней,
  средняя длина проживания). Итоги у такой строки не считаются — дублировали бы её.
- Тип колонки выводится из расчёта: count → целое, доля ×100 → процент, avg → число.

**Аудит.** `/reports` добавлен в `TRACKED_PREFIXES`, но `run/export/preview/validate`
исключены регэкспом (`IGNORED_PATTERNS`) — иначе журнал утонул бы в запусках.
Сокет `reports:changed` — другие рабочие места перечитывают список.

**Гочи.** Группировка «выбирает пользователь» — это параметр `groupBy` (select) +
`groupBy: { param }`; секция «Группировка» держит его синхронно сама, руками его
не править. Поля-списки в конструкторе («a, b», «значение | подпись») пишутся в
определение по blur/Enter, не на каждую букву (`editor/deferred.tsx`).

**Файлы:** `server/src/reports/{registry,vocab}.js`, `controllers/reportController.js`,
`routes/reports.js`, `middleware/{audit,errorHandler}.js` (проброс `problems`),
`client/src/components/Reports/editor/` (ReportEditor, model, ui, deferred, sections/),
`client/src/api/reports.ts`, `prisma/schema.prisma` + `electron/db/init.sql`.

### Отчёты: отчёт — это ДАННЫЕ, а не код (2026-09-03)
**Развилка.** Отчёты можно было написать как обычные контроллеры («загрузка», «реестр»).
Но в планах — настройка доступа к каждому отчёту, редактор, конструктор с нуля и
**импорт**: сложный отчёт под заказчика проще сгенерировать файлом и загрузить клиенту,
чем собирать руками в конструкторе. На захардкоженные контроллеры это не положить.

**Решение — два слоя.**
1. **Датасеты** (код, их мало): `bookings` — строка = бронь; `roomNights` — строка =
   номер × ночь. Каждый описывает свои поля (`fields`: подпись, тип, `groupable`) —
   это контракт, из которого конструктор построит свой UI, а не документация.
2. **Определение отчёта** (данные, JSON): параметры, фильтры, группировка, колонки,
   агрегаты, сортировка. Их правит редактор, создаёт конструктор, приносит импорт.

**Конструктор не пишет SQL — и не должен.** Определение только выбирает поля датасета
и операции из закрытого списка (`OPS`, `AGGS`). Поэтому чужой импортированный файл не
опаснее набора настроек. Это и есть причина, по которой между «определением» и базой
стоит датасет.

**Почему `roomNights` разворачивает брони в ночи.** Загрузка по дням, по категориям и по
корпусам — это ОДИН куб с разной группировкой, а не три отчёта. Три состояния ночи:
`sold` / `blocked` (ремонт, `source='ремонт'`) / `free`; доступный фонд = всё минус ремонт.
Решено показывать ремонт отдельной колонкой и вычитать из знаменателя: видно и честную
загрузку, и сколько фонда выбито из продажи.

**Найденная ошибка старого кода.** `avgOccupancy` считался как СРЕДНЕЕ ПРОЦЕНТОВ по
номерам. При разном числе доступных ночей это врёт: на июле 2024 по категориям выходило
5.8% вместо верных 9.7%. Теперь доля считается от сумм (`ratio`), в том числе в итогах.

**Выгрузка — один модуль на все отчёты** (`reports/export.js`): на входе только
`{columns, rows, totals}`, поэтому новый отчёт получает CSV/Excel/Word сразу.
CSV — `;` и десятичная запятая + BOM (открывается двойным кликом в русском Excel).
**PDF сознательно не серверный:** его делает Electron через `printToPDF` из того же окна,
что уходит на принтер, — иначе появился бы второй движок вёрстки и PDF разошёлся бы
с бумагой. Печать и PDF используют один блок `#report-print` и `@media print` в `theme.css`;
отдельной «версии для печати» нет намеренно.

**Ограничения (осознанные).** `roomNights` — максимум 400 дней за раз (иначе куб на
годы × сотни номеров). На экране 5000 строк, в файл — до 50 000. Деактивированные
номера в фонд не входят по их ТЕКУЩЕМУ состоянию: истории фонда в схеме нет, и
отчёт за прошлый год посчитает его по сегодняшнему списку номеров.

**Что удалено.** Старые `GET /api/reports/{occupancy,bookings}` и заглушки `/revenue`
(TODO) и `/export` (501). Клиент их не вызывал, а две реализации загрузки разошлись бы
в цифрах.

**Финансовых отчётов пока нет и не может быть:** в базе 0 строк `BookingCharge`, у всех
броней `totalAmount = 0`, платежей как сущности не существует. Выручка — после генератора
начислений, касса за смену — после журнала платежей (см. запись про ценообразование выше).

**Файлы:** `server/src/reports/` (dateUtils, datasets/, engine, registry, options, export,
definitions/*.json), `controllers/reportController.js`, `routes/reports.js`,
`client/src/api/reports.ts`, `client/src/components/Reports/`, `electron/main.js`
(`report:savePdf`, `report:saveFile`). Новые зависимости сервера: `exceljs`, `docx`.

### Починка блоков C, D, E (2026-09-03, вторая волна)
Три агента параллельно по разведённым файлам; проверено API-прогоном (22 проверки)
и в браузере. Не закоммичено.
- **C1. Вход.** `authenticate` различает битый токен (401) и сбой базы (503 «Сервер
  временно недоступен») — раньше секундный рестарт Postgres разлогинивал всех. Перехватчик
  401 на клиенте не трогает запросы входа и мастера; `restore()` стирает токен только
  на 401/403. Экран входа показывает текст сервера, «Сервер недоступен…» и текст лимитера.
- **C2.** Флаг «Ранний выезд» сбрасывается при открытии формы; диалог накрывает только
  форму (контейнеру дан `position: relative`).
- **C3. Права.** `POST /shifts/next-day` и `/occupancy/optimize/apply` — только
  SUPER_ADMIN/ADMIN; отмена заселённого гостя — тоже (403). В интерфейсе: контекстное меню
  прячет «Редактировать/Удалить» для закрытых броней и «Удалить» заселённого для STAFF;
  в оптимизаторе STAFF не видит «Применить»; кнопка «Следующий день» в «Аудит → Смены»
  только администраторам и с подтверждением, где написана дата.
- **C4.** У заселённого гостя нельзя поставить выезд не позже рабочей даты (иначе номер
  «освобождался» при живом госте); `checkOut` отказывает, если рабочая дата раньше заезда.
- **D1.** Мутации номеров, категорий и партнёров сбрасывают кэш сетки (`invalidateGridCache`).
- **D2. Шапка сетки.** Выходные считаются как в строках (`T12:00:00Z` + `getUTCDay`).
  Шапка осталась снаружи прокручиваемого тела, но обёрнута в `overflow: hidden` и её
  `scrollLeft` ведётся из `onScroll` тела; ширина дня считается с вычетом измеренной
  вертикальной полосы прокрутки (ResizeObserver), так что при штатных 30 днях
  горизонтального скролла нет вовсе. Вариант «шапка внутри контейнера» отвергнут:

### Починка блоков A и B + мастер первого запуска (2026-09-03)
По отчёту «main problems» (папка «Qonaq — документы») закрыты блоки A и B; делали четырьмя
агентами параллельно (файлы разведены, чтобы не пересекались), проверено API-прогоном
(27 проверок) и в браузере. Все правки не закоммичены — лежат в рабочей копии.
- **A1. Редактирование брони больше не обнуляет деньги.** Сетка отдаёт бронь целиком
  (гости, скидка, суммы), а форма при открытии всегда догружает бронь с сервера
  (`fetchBooking`) и держит «Сохранить» заблокированной, пока грузится.
- **A2. Итог не пересчитывается без причины.** В режиме правки сумма уходит на сервер,
  только если изменились входы калькулятора (даты, категория, гости, скидка, предоплата)

  без тарифа → «итог не рассчитан» (ноль — не цена); ночи вне сезонов помечаются
  предупреждением. Календарь цен (`RatePrice`) к расчёту пока НЕ подключён — следующий шаг.
- **A3. Валидация и ошибки.** Числа проверяются на POST и PUT (`routes/bookings.js`),
  PUT получил те же правила, что POST; `errorHandler` переводит P2003 / P2010(23503) /

  и скрытые номера; `grid`/`availability`/`check-availability` валидируют query.
- **B1. Переезд со сплитом не работал никогда:** `createdById` → `adminId`; вторая часть

- **B2. Оптимизатор применяется.** Ограничение `booking_no_overlap` пересоздано как

- **Мастер первого запуска и системные настройки.** Две разные роли: **сисадмин** — ставит

### Ценообразование: бронь — это СУММА СТРОК, а не результат формулы (2026-09-02)
Главная развилка проекта. Задача, как её сформулировал Абзал: маленькие отели гибкие,
и эта гибкость ломает жёсткие системы учёта — деньги в системе расходятся с деньгами
на руках.

**Ключевой вывод:** расходятся они не из-за нехватки настроек, а потому что уступки
происходят МИМО системы. Администратор пошёл навстречу, посчитал в уме, вписал итог.
Значит цель не «предусмотреть все правила всех отелей» (недостижимо и порождает
мешанину галочек), а **сделать так, чтобы любое отступление от правил было записано**.

**Модель.** Тариф лишь ПОРОЖДАЕТ строки начислений (`BookingCharge`, `source='auto'`).
Итог брони = сумма строк. Строку можно поправить, удалить или добавить свою
(`source='manual'` + обязательная `reason` + автор). `Booking.totalAmount` становится
кэшем суммы, а не самостоятельным числом.

Живые случаи, ради которых это делалось:
- **«Заехали в 01:00, беру полсуток»** → строка-скидка с причиной и автором.
  Через месяц видно, кто и почему уступил, и сумма сходится с кассой.
- **«Три дня, но только завтрак»** → убрали строки «Обед» и «Ужин». Не нужна опция
  «только завтрак» — нужна возможность убрать строку. Завтра появится отель
  с «завтрак + ужин» — заработает без единой правки кода.

**Принятые ответы на развилки (2026-09-02):**
- **За номер или за человека** — одна настройка на весь объект (`HotelSettings.pricingBase`).
  Меняется только генератор строк, вид строк одинаковый.
- **Несколько тарифов на один номер — НЕ нужны.** Цена определяется категорией и датой.
  Скидки партнёрам — процентом или ручной строкой.
- **Цена — календарь по дням**, а не диапазоны-сезоны. НО заполняется диапазонами
  (иначе год = 365 правок), с фильтром по дням недели. То есть сезоны остались
  способом ВВОДА, а не структурой данных, и поверх всегда можно поправить одну дату
  вроде 31 декабря.
- **Питание — это не флаг брони, а обычные услуги** (`Service`): завтрак, обед, ужин
  по отдельности. «Полный пансион» / «Полупансион» / «Только завтрак» — пресеты
  (`MealPlan`), то есть кнопки над теми же переключателями. Как с метками броней.

**Чего одного прайса НЕ хватит.** Гибкие цены отвечают «сколько гость должен».
Чтобы сходилось с наличными, нужен второй журнал — платежи (кто принял, когда, чем,
в какую смену). Сейчас `paidAmount` — число без истории, по нему смену не закрыть.
Платежи вторым этапом, но модель начислений заложена с расчётом на них.

**Что уже сделано:** схема (`HotelSettings`, `RatePrice`, `Service`, `MealPlan`,
`BookingCharge`) + `init.sql`; API `/api/hotel` и `/api/rates`.
Массовое заполнение календаря — одним SQL с `generate_series` и
`ON CONFLICT DO UPDATE COALESCE(...)`: 4 категории × 180 дней это 720 строк, циклом
upsert'ов было бы 720 обращений к БД. COALESCE важен: правка одной цены не затирает
остальные.

**Что осталось:** экран «Тарифы и наличие» (он же закроет заглушку в меню),
генератор начислений, переделка расчёта в `BookingModal`, услуги и пресеты питания,
перенос `PricingConfig` из localStorage.

### Многопользовательская работа = локальный сервер в одной сети (2026-06-18)
- **Модель:** один ноут — **хост** (на нём Postgres + Node-сервер), остальные ноуты —
  Electron-клиенты, обращаются к хосту по **локальной сети**. Наружу (в интернет) ничего
  не выставляется — работает только внутри LAN/Wi-Fi гостиницы. Для нашего случая это ок.
- **Почему:** это desktop-программа (не веб-сервис); общая БД нужна, чтобы оба админа

- **Что уже готово:** сервер слушает `0.0.0.0` (`server.js`), broadcast Socket.io летит
  всем клиентам (`socketManager.js`) → realtime между ноутами заработает сам.

  (2) клиент должен знать адрес хоста — сейчас в `client/src/api/client.ts` относительные URL

### Метки броней — источник истины в БД
- Модель `BookingFlag` (`code`, `label`, `effects` JSON, `color`, `order`).
- `Booking.flags[]` хранит `code`. Клиент подгружает метки из БД в стор при входе,
  поэтому грид/модалка/оптимизатор работают как раньше (форма `{id,label,effects}`, `id`=`code`).
- Эффекты применяются: в оптимизаторе, при создании и изменении брони (буфер turnaround).

### Система эффектов меток (алгоритм понимает не названия, а эффекты)
- Принцип: метка = ярлык + список **эффектов** из фиксированного словаря. Алгоритм
  работает только с эффектами. Новая метка из существующих эффектов = **0 кода**.
- Текущий словарь: `bufferAfter` (зазор после, напр. поздний выезд=1), `bufferBefore`,
  `pin` (не перемещать).
- Буфер делает двойную работу: запрещает бронь день-в-день + не даёт оптимизатору считать
  этот зазор «окном».

### Оптимизатор: «улучшение от текущей раскладки» (минимум ходов)
- Стартует с реальной раскладки, делает только строго улучшающие ходы (перенос + обмен),
  каждый ход стоит `movePenalty` → предлагаются только осмысленные перестановки.
- Двигает **только не заехавшие** брони (CONFIRMED, не оплачено, не pin, заезд в будущем).
  Заехавшие/оплаченные/ремонт = якоря. Поэтому «переселения гостя» нет — это смена номера
  на бумаге до приезда.
- У каждого хода считается маржинальный эффект «−N окон/ночей» (аннотация, движок не меняет).

### Правила/грабли
- **Новая таблица = ДВЕ правки, а не одна.** Миграций нет, проект на `db push`.
  `db push` меняет только твою локальную базу; свежая установка разворачивается из
  `electron/db/init.sql`. Значит после правки `schema.prisma` таблицу/индексы нужно
  **вручную дописать в `init.sql`**, иначе у нового клиента её просто не будет.
  Забудешь — узнаешь только при установке с нуля. Так делали для `Contact` (2026-09-02).
  Настоящее лечение — перейти на `prisma migrate` (см. отчёт по готовности).
- **Сервер в dev — обычный `node server.js`, не nodemon:** правки в `server/` сами
  не подхватываются, перезапускай руками. В `.claude/launch.json` есть конфиг
  «Hotel Server» (запуск из Claude Code); он же выставляет `SNAPSHOT_KEEP_AUTO=60`,
  чтобы тестовые прогоны не вытесняли твои авто-снимки (штатно хранится 15).
- **`prisma/sql/booking_no_overlap.sql` идемпотентный** (DROP IF EXISTS + ADD …
  DEFERRABLE INITIALLY IMMEDIATE), применять можно повторно; тот же текст в `init.sql`.
- **Пароль сисадмина** лежит в `%APPDATA%\hotel-booking-desktop\config.json`
  (`sysadmin: { salt, hash }`). Забыли — удалить этот ключ из файла: окно «Настройка
  системы» откроется без пароля и попросит задать новый.
- **Prisma generate падает с EPERM**, если сервер запущен (держит DLL). Перед
  `npx prisma db push` / `generate` сначала останови node. Гасить ВСЕ node-процессы
  необязательно — найди тот, что слушает 3001:
  `Get-NetTCPConnection -LocalPort 3001 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }`.
- **CSS-ловушка:** `transform` на родителе делает его containing block для
  `position: fixed` детей → ломает меню/тултипы в гриде. В строках сетки позиционируем
  через `top`, не `transform`.
- **Даты `@db.Date`** хранятся как UTC-полночь. Везде используем `Date.UTC(...)` и
  рендерим с `timeZone:'UTC'`, иначе сдвиг на день.
- **Detached-сервер `node server.js` НЕ перезапускается сам** при правке кода — нужен
  ручной рестарт (nodemon только при `npm run dev` в foreground).
