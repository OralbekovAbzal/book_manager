# Брони и алгоритмы — принятые решения

Брони, смены, метки, оптимизатор, квоты. Живая часть журнала — в `hotel-booking/NOTES.md`.

### Дата смены хранится в БД (не берётся с устройства)
- «Рабочий день» = дата последней смены (`Shift`), меняется **только вручную** кнопкой
  «Следующий день». Нигде не берём дату устройства для бизнес-логики.
- Реализация: `server/src/utils/businessDate.js` (`getCurrentBusinessDate`). Используется
  в гриде, бронях, оптимизаторе, проверке «прошедших дат».

### Метки броней — источник истины в БД
- Модель `BookingFlag` (`code`, `label`, `effects` JSON, `color`, `order`).
- `Booking.flags[]` хранит `code`. Клиент подгружает метки из БД в стор при входе,
  поэтому грид/модалка/оптимизатор работают как раньше (форма `{id,label,effects}`, `id`=`code`).
- Эффекты применяются: в оптимизаторе, при создании и изменении брони (буфер turnaround).

### Система эффектов меток (алгоритм понимает не названия, а эффекты)
- Принцип: метка = ярлык + список **эффектов** из фиксированного словаря. Алгоритм
  работает только с эффектами. Новая метка из существующих эффектов = **0 кода**.
- Текущий словарь: `bufferAfter` (зазор после, напр. поздний выезд=1), `bufferBefore`,
  `pin` (не перемещать).
- Буфер делает двойную работу: запрещает бронь день-в-день + не даёт оптимизатору считать
  этот зазор «окном».

### Оптимизатор: «улучшение от текущей раскладки» (минимум ходов)
- Стартует с реальной раскладки, делает только строго улучшающие ходы (перенос + обмен),
  каждый ход стоит `movePenalty` → предлагаются только осмысленные перестановки.
- Двигает **только не заехавшие** брони (CONFIRMED, не оплачено, не pin, заезд в будущем).
  Заехавшие/оплаченные/ремонт = якоря. Поэтому «переселения гостя» нет — это смена номера
  на бумаге до приезда.
- У каждого хода считается маржинальный эффект «−N окон/ночей» (аннотация, движок не меняет).
