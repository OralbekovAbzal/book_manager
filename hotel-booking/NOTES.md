## 🟢 Активные идеи / направления (что делать дальше)

### Справочник → вкладка «Гости» (2026-09-02)
**Идея:** собрать адресную книгу постояльцев из уже существующих броней — заводить
руками ничего не надо, данные копятся сами.
- **Что показывать:** карточка гостя = имя, телефон, сколько раз жил, всего ночей,
  последний визит + список его броней с переходом к ним в шахматке.
- **Ключ группировки — телефон, а не имя.** Имя пишут по-разному («Асель»,
  «Асель К.», «Асель Каримова»), номер один. По имени склеятся разные люди.
- **Что вылезет на живых данных:** номера записаны как попало (`+7 701…`, `8701…`,
  со скобками и пробелами) — для базы это разные строки, нужна нормализация при
  сравнении, иначе один гость размножится на несколько карточек.
- **Брони без телефона** (поле необязательное) в список не попадут. Показать их
  отдельной кучкой честнее, чем группировать по имени и соврать.
- **Зачем:** решает реальную боль стойки — «звонит гость, бронировал на июль».
  Сейчас найти его можно только листая шахматку. Плюс «постоянный гость, дайте скидку».
- **Оценка:** ~полдня, если не считать возню с нормализацией телефонов.

### Пресет контактов на свежей установке (2026-09-02)
Справочник на новой установке пустой → на демо выглядит недоделанным. Засеять то,
что одинаково у всех: 103 / 101 / 102, аварийная газовая, горводоканал, электросети.
Клиент открывает — там уже осмысленный список, остаётся дописать своего сантехника.
Та же логика «пресеты вместо настройки», что и с метками броней (см. ниже).

### Пресеты особенностей и меток (главное направление по оптимизатору)
**Идея (твоя):** не заставлять пользователя настраивать эффект каждой метки/особенности.
Вместо этого — заранее сделать **большую готовую библиотеку** особенностей и меток
с уже прописанными эффектами. Пользователь просто **скрывает ненужные** и пользуется
нужными. Мы один раз продумываем словарь и пресеты — клиент только вкл/выкл.
- **Почему важно:** сам алгоритм — простая часть, сложное — настройка под каждую базу.
  Пресеты снимают эту сложность для нетех-пользователя.
- **Что уже готово под это:** метки с эффектами хранятся в БД (`BookingFlag`),
  движок понимает словарь эффектов (буфер до/после, «не перемещать»).
- **Что осталось:** наполнить библиотеку пресетов; заменить «удалить» на «скрыть/показать»
  (поле `hidden`/`isActive` у метки и особенности); продумать список стандартных
  особенностей (типы кроватей, балкон, вид, этаж- only и т.д.) с эффектами по умолчанию.

### Путь оптимизатора во «флагман» (по убыванию ценности)
1. **Подбор под запрос** 🥇 — «есть на 5 ночей с 3 июля?»: мгновенный ответ + если не
   помещается, предложить микро-перестановку неподтверждённых броней. Превращает
   оптимизатор из пассивного в инструмент продаж (ловит брони, которые иначе теряются).
2. **Счётчик потерянной выручки** — «за месяц отвернули N запросов = X тенге». Нужен
   мини-журнал отказов.
3. **Подсказка при заведении брони** — класть новую бронь сразу оптимально (профилактика
   фрагментации вместо лечения).
4. **Цель = выручка, а не окна** — взвешивать окна по цене/сезону (yield management).
5. **Автопилот** — система сама держит сетку чистой, сигналит только при реальной выгоде.

### Расширение словаря эффектов меток
Те же «кубики», добавляются по одному (обработчик в движке + поле в форме метки):
- **Только этажи […]**, **Только корпуса […]**, **Требует особенность […]**.
- Каркас готов: `optimizeController.js` (буферы/pin) + `utils/flagEffects.js`.

## ✅ Принятые решения (что и почему сделано так)

### Справочник контактов — сделан, данные в БД (2026-09-02)
Раздел «Справочник» из бокового меню (был заглушкой) теперь открывает экран контактов:
сотрудники, службы, подрядчики, экстренные номера.
- **Модель `Contact`** (`schema.prisma`): имя, должность, группа, до 5 телефонов,
  почта, заметка, `isPinned`, мягкое удаление через `isActive`.
  API: `server/src/controllers/contactController.js` + `routes/contacts.js`.
  Читают все, правят ADMIN и SUPER_ADMIN.
- **В БД, а не в localStorage** — иначе разъедется между ноутами, как уже разъезжаются
  корпуса, особенности и тарифы (см. TODO).
- **Группы фиксированы пресетом** (Экстренные / Сотрудники / Службы отеля /
  Подрядчики / Прочее) — клиент их не настраивает, только заполняет записи.
- **Экран:** `client/src/components/Reference/ReferenceWindow.tsx`. Построен вокруг
  поиска (имя, должность, заметка + по цифрам номера, игнорируя `+7`, скобки и пробелы).
  Чипы групп со счётчиками, живыми по текущему поиску. Клик по номеру копирует его.
  Печать списка на A4 — через скрытый iframe (`window.open` в Electron перехватывается
  и уводит страницу во внешний браузер).
- **Горячая клавиша F2** открывает/закрывает справочник из любого места.
- ⚠️ **Таблицу пришлось вручную дописать в `electron/db/init.sql`** — миграций нет,
  `db push` про свежие установки не знает. Это цена отсутствия миграций (см. TODO).

### Разделы — настоящая навигация, а не окна поверх сетки (2026-09-02)
Шли к этому в три шага, итог такой: **шахматка сама заменяется выбранным разделом**.
- **Было:** «Настройки» и «Справочник» — `position: fixed; inset: 0`, окна ПОВЕРХ
  шахматки. Сначала они перекрывали ещё и шапку (правили через `top: var(--topbar-h)`),
  но корень был глубже: они притворялись экранами, оставаясь модалками.
- **Стало:** в `App.tsx` одно состояние `section: NavSection` — какой экран занимает
  область под шапкой. Разделы — обычные элементы потока (`flex: 1; min-height: 0`),
  без `position: fixed` и без возни с z-index.
- **Обвязка шахматки уходит вместе с ней:** `TodayStats` (полоса дат), `Filters`
  и `StatusBar` рендерятся только при `section === 'grid'` — они принадлежат сетке,
  а не приложению.
- **Что осталось модалками:** бронь, просмотр, перемещение, удаление, контекстное меню,
  аудит, снапшоты, оптимизатор. Это действия, а не места. Форма контакта в справочнике —
  тоже модалка (см. ниже).
- **`--topbar-h: 52px`** в `theme.css` остаётся: шапка общая для всех разделов.
- Пункты «Тарифы и наличие» и «Отчёты» показывают заглушку «Раздел ещё не готов» —
  с настоящей навигацией мёртвый клик выглядел бы поломкой. **Перед показом клиенту
  эти пункты лучше убрать из меню совсем** (см. TODO).
- Побочно: кнопка «Настройки» убрана из шапки (2026-09-02) — раздел открывается
  из меню по клику на эмблему «H». Определение иконки в коде оставлено.

### Форма контакта — модальным окном (2026-09-02)
Сначала форма открывалась сверху списка: нажимаешь карандаш на нижней карточке —
форма появляется за пределами экрана, визуально **не происходит ничего**.
- Теперь модалка по центру, как у брони и перемещения. Escape закрывает **сначала
  форму**, и только потом раздел — иначе одно нажатие выбрасывало бы из справочника
  вместе с недописанной записью.
- Кнопка **«Сохранить и добавить ещё»**: окно остаётся, поля чистятся, выбранная
  группа сохраняется, курсор возвращается в поле имени. Первичное заполнение
  справочника — это десяток записей подряд.

### Многопользовательская работа = локальный сервер в одной сети (2026-06-18)
- **Модель:** один ноут — **хост** (на нём Postgres + Node-сервер), остальные ноуты —
  Electron-клиенты, обращаются к хосту по **локальной сети**. Наружу (в интернет) ничего
  не выставляется — работает только внутри LAN/Wi-Fi гостиницы. Для нашего случая это ок.
- **Почему:** это desktop-программа (не веб-сервис); общая БД нужна, чтобы оба админа
  видели одни брони. Один источник истины = одна машина с базой.
- **Что уже готово:** сервер слушает `0.0.0.0` (`server.js`), broadcast Socket.io летит
  всем клиентам (`socketManager.js`) → realtime между ноутами заработает сам.
- **Что нужно настроить (TODO ниже):** (1) на хосте — статический/закреплённый локальный IP;
  (2) клиент должен знать адрес хоста — сейчас в `client/src/api/client.ts` относительные URL
  (`/api`, `io('/')`), в упакованном Electron они ни к чему не резолвятся → нужно вынести
  base URL в конфиг (напр. `http://<IP-хоста>:3001`); (3) CORS/`CLIENT_ORIGIN` пустить
  origin клиентов; (4) брандмауэр Windows — открыть порт 3001 на хосте.

### Дата смены хранится в БД (не берётся с устройства)
- «Рабочий день» = дата последней смены (`Shift`), меняется **только вручную** кнопкой
  «Следующий день». Нигде не берём дату устройства для бизнес-логики.
- Реализация: `server/src/utils/businessDate.js` (`getCurrentBusinessDate`). Используется
  в гриде, бронях, оптимизаторе, проверке «прошедших дат».

### Метки броней — источник истины в БД
- Модель `BookingFlag` (`code`, `label`, `effects` JSON, `color`, `order`).
- `Booking.flags[]` хранит `code`. Клиент подгружает метки из БД в стор при входе,
  поэтому грид/модалка/оптимизатор работают как раньше (форма `{id,label,effects}`, `id`=`code`).
- Эффекты применяются: в оптимизаторе, при создании и изменении брони (буфер turnaround).

### Система эффектов меток (алгоритм понимает не названия, а эффекты)
- Принцип: метка = ярлык + список **эффектов** из фиксированного словаря. Алгоритм
  работает только с эффектами. Новая метка из существующих эффектов = **0 кода**.
- Текущий словарь: `bufferAfter` (зазор после, напр. поздний выезд=1), `bufferBefore`,
  `pin` (не перемещать).
- Буфер делает двойную работу: запрещает бронь день-в-день + не даёт оптимизатору считать
  этот зазор «окном».

### Оптимизатор: «улучшение от текущей раскладки» (минимум ходов)
- Стартует с реальной раскладки, делает только строго улучшающие ходы (перенос + обмен),
  каждый ход стоит `movePenalty` → предлагаются только осмысленные перестановки.
- Двигает **только не заехавшие** брони (CONFIRMED, не оплачено, не pin, заезд в будущем).
  Заехавшие/оплаченные/ремонт = якоря. Поэтому «переселения гостя» нет — это смена номера
  на бумаге до приезда.
- У каждого хода считается маржинальный эффект «−N окон/ночей» (аннотация, движок не меняет).

### 🔒 Аудит безопасности (2026-06-18) — что нашли в backend
Полный проход по auth/JWT/валидации/инъекциям/секретам. По убыванию критичности:

- [ ] **🔴 КРИТ. Слабый угадываемый `JWT_SECRET`.** `server/.env:11` =
      `hotel-booking-secret-key-minimum-32-chars-long` — это не случайная строка, а

### 🧮 Аудит бизнес-логики броней (2026-06-18) — переходы статусов vs смена
Проход по `bookingController.js`: даты/смена vs статусы. Суть: переходы статусов и
прямой статус при создании НЕ сверяются с бизнес-датой (датой смены). Общее правило-фикс:
**CHECKED_IN допустим только когда `businessDate >= booking.checkIn`** + единый запрет
прошлых дат в `create` И `update`. На текущих (тестовых) данных живых случаев нет, но код
их пропускает.

- [x] **✅ ИСПРАВЛЕНО (2026-06-18). `checkIn` сверяется со сменой** (`bookingController.js`).
      Добавлена проверка `businessDate < checkInUTC` → нельзя отметить «заехал» раньше даты
      заезда брони (поздний заезд оставлен). Требует рестарт сервера.
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). `create` не создаёт «заехавшим» на будущее**
      (`bookingController.js`). Если дата заезда впереди смены (или это ремонт) — статус
      принудительно сбрасывается в `CONFIRMED`. Требует рестарт сервера.
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). Бэкдейтинг в `update` закрыт** (`bookingController.js`).
      Перенос заезда на дату < смены отклоняется (как в `create`); ремонт по-прежнему можно
      задним числом. Требует рестарт сервера.
- [ ] **🟠 `checkOut` может выдать бронь с `checkOut < checkIn`** (`bookingController.js:371`).
      Если бронь отметили «заехал» рано (баг выше) и сразу выезд: `todayUTC < checkOut` →
      ставит `checkOut = todayUTC` < `checkIn` → невалидная бронь. Корень — баг №1, но `checkOut`
      стоит защитить отдельно.
- [ ] **🟠 `checkOut` день-в-день молча УДАЛЯЕТ бронь физически** (`bookingController.js:363`).
      `prisma.booking.delete` — реальное удаление из БД, тогда как `cancel` принципиально не
      удаляет (стр. 291). Потеря записи/истории/аудита. **Фикс:** ставить `CANCELLED`, а не delete.
- [ ] **🟡 `move` — проверка пересечений вне транзакции** (`bookingController.js:447`): `findOverlap`
      идёт ДО `$transaction`, а same-day-ветка (стр. 426) вообще без транзакции → тот же класс
      race condition, что и в `create`.
- [ ] **🟡 `move` сплит обнуляет деньги на новой брони** (`bookingController.js:490`):
      `totalAmount/prepaidAmount/paidAmount = 0` → оплата «теряется» на переехавшей части.
      Всплывёт, когда начнём заполнять цены (см. TODO про цены).
- [x] **✅ ИСПРАВЛЕНО (2026-06-18). «Ремонт» нельзя отметить «заехал»** (`bookingController.js`):
      `checkIn` теперь отклоняет брони с `source==='ремонт'`. Требует рестарт сервера.

- [x] **✅ ИСПРАВЛЕНО (2026-06-18). Двойное бронирование (race condition) — был ПРИОРИТЕТ №1.**
      В БД добавлен **exclusion-constraint** `booking_no_overlap`:
      `EXCLUDE USING gist (roomId WITH =, daterange(checkIn,checkOut) WITH &&) WHERE status
      IN ('CONFIRMED','CHECKED_IN')` + `CREATE EXTENSION btree_gist`. Теперь БД **физически
      запрещает** пересечение активных броней — даже при одновременном сохранении двумя
      админами второй INSERT/UPDATE отклоняется. `errorHandler.js` ловит нарушение и отдаёт
      дружелюбный 409. Транзакции НЕ понадобились — constraint и есть гарантия.
      - SQL: `server/prisma/sql/booking_no_overlap.sql` (применён напрямую через
        `npx prisma db execute`, т.к. проект на `db push`, миграций нет).
      - Перед применением проверено: существующих пересечений в базе не было.
      - **Откат:** `ALTER TABLE "Booking" DROP CONSTRAINT booking_no_overlap;`
      - Код errorHandler требует рестарт сервера; constraint уже активен в БД.
- [ ] **Совместная работа двух ноутов = нужна одна общая БД-машина.** (2026-06-18)
      Это desktop-программа (Electron), web-режим — только для разработки, чтобы не
      пересобирать exe. Значит каждый ноут со своим локальным Postgres = **отдельные базы**,
      броней друг друга не видят. Для совместной работы один ПК/ноут хостит Postgres + Node,
      остальные Electron-клиенты подключаются к нему по локальной сети (`DATABASE_URL` и
      адрес API указывают на IP сервера). Код к этому готов: `HOST=0.0.0.0`, относительные
      URL в `client/src/api/client.ts`, broadcast в `socketManager.js` (realtime между
      клиентами уже рассылается всем). Топология **выбрана** — LAN-хост (см. «Принятые
      решения»). Осталось реализовать: base URL клиента в конфиг, CORS/`CLIENT_ORIGIN`,
      статический IP хоста, открыть порт 3001 в брандмауэре.

### Запуск (detached, переживает сессию) — PowerShell
```powershell
# Backend
Start-Process -FilePath "node" -ArgumentList "server.js" `
  -WorkingDirectory "...\hotel-booking\server" -WindowStyle Hidden `
  -RedirectStandardOutput "...\.logs\server.out.log" -RedirectStandardError "...\.logs\server.err.log"
# Frontend (npm — это .cmd!)
Start-Process -FilePath "npm.cmd" -ArgumentList "run","dev" `
  -WorkingDirectory "...\hotel-booking\client" -WindowStyle Hidden ...
```
Логи: `hotel-booking/.logs/`.

### Правила/грабли
- **Новая таблица = ДВЕ правки, а не одна.** Миграций нет, проект на `db push`.
  `db push` меняет только твою локальную базу; свежая установка разворачивается из
  `electron/db/init.sql`. Значит после правки `schema.prisma` таблицу/индексы нужно
  **вручную дописать в `init.sql`**, иначе у нового клиента её просто не будет.
  Забудешь — узнаешь только при установке с нуля. Так делали для `Contact` (2026-09-02).
  Настоящее лечение — перейти на `prisma migrate` (см. отчёт по готовности).
- **Prisma generate падает с EPERM**, если сервер запущен (держит DLL). Перед
  `npx prisma db push` / `generate` сначала останови node. Гасить ВСЕ node-процессы
  необязательно — найди тот, что слушает 3001:
  `Get-NetTCPConnection -LocalPort 3001 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }`.
- **CSS-ловушка:** `transform` на родителе делает его containing block для
  `position: fixed` детей → ломает меню/тултипы в гриде. В строках сетки позиционируем
  через `top`, не `transform`.
- **Даты `@db.Date`** хранятся как UTC-полночь. Везде используем `Date.UTC(...)` и
  рендерим с `timeZone:'UTC'`, иначе сдвиг на день.
- **Detached-сервер `node server.js` НЕ перезапускается сам** при правке кода — нужен
  ручной рестарт (nodemon только при `npm run dev` в foreground).
