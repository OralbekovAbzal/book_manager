### 0.1. Где живёт `booking_no_overlap` — противоречие разведки разрешено

**В обоих местах, и это не ошибка.**

1. `server/prisma/migrations/0_init/migration.sql:475-484` — часть базовой миграции (НЕ идемпотентный вариант):
   ```sql
   CREATE EXTENSION IF NOT EXISTS btree_gist;

   ALTER TABLE "Booking"
     ADD CONSTRAINT booking_no_overlap
     EXCLUDE USING gist (
       "roomId" WITH =,
       daterange("checkIn", "checkOut") WITH &&
     )
     WHERE (status IN ('CONFIRMED', 'CHECKED_IN'))
     DEFERRABLE INITIALLY IMMEDIATE;
   ```
   Комментарий над ним (`:468`): «Тот же текст (идемпотентный вариант) — server/prisma/sql/booking_no_overlap.sql».
2. `server/prisma/sql/booking_no_overlap.sql:15-26` — идемпотентный вариант (`DROP CONSTRAINT IF EXISTS` + `ADD … DEFERRABLE INITIALLY IMMEDIATE`), для ручного применения `prisma db execute`.

Следствия:
- Свежая установка (`migrate deploy` на пустой базе) получает constraint из `0_init` — NOTES («в ней же лежит exclusion-constraint») верен. `test-host.mjs:61-62` это проверяет.
- Повторное применение `sql/` на базе из миграций безопасно (DROP IF EXISTS + ADD) — подтверждено текстом файла.
- **В dev-базе** (MCP): `booking_no_overlap` есть, `contype=x`, `condeferrable=true`, `condeferred=false` (INITIALLY IMMEDIATE), `btree_gist 1.7`; `_prisma_migrations` — 8 строк, `0_init` с `applied_steps_count=0` (baseline через `resolve --applied`, SQL не выполнялся — constraint в dev-базе появился из `sql/`, применённого вручную 03.09).
- **Дыра только для dev** (см. D8-019): база, собранная `db push` и помеченная `db:migrate:baseline`, constraint из `0_init` **не получает** (resolve не выполняет SQL) — `sql/` нужно применять руками, иначе `optimize/apply` упадёт на `SET CONSTRAINTS booking_no_overlap DEFERRED`.
- NOTES «Правила/грабли» всё ещё говорит «тот же текст в `init.sql`» — файла нет с 04.09 (D8-022).

### 0.2. На каком интерфейсе слушает встроенный Postgres (5433)

**Только loopback. По LAN база недоступна даже с паролем из `config.json`.**

- `embedded-postgres/dist/index.js:206-212`: `postgres.exe` запускается только с `-D <dataDir> -p <port>` + `postgresFlags` (в `main.js:135-145` они не заданы). `listen_addresses` не передаётся → действует умолчание `postgresql.conf` = `'localhost'`. Подтверждено в установленной программе: `%APPDATA%\hotel-booking-desktop\pgdata\postgresql.conf:60` — строка `#listen_addresses = 'localhost'` закомментирована (умолчание).
- `initdb` (`index.js:152-159`) вызывается с `--auth=password` (умолчание `authMethod: 'password'`, `index.js:54`) → `pg_hba.conf` установленной программы (без комментариев):
  ```
  local   all   all                 password
  host    all   all   127.0.0.1/32  password
  host    all   all   ::1/128       password
  ```
  Записей для LAN-подсетей нет. Даже если бы `listen_addresses` открыли, `pg_hba` отклонил бы соединение.
- Нюанс: `--auth=password` = пароль в открытом виде по сети (не `scram-sha-256`), но трафик только loopback — приемлемо. Пароль на время `initdb` пишется в `%TEMP%\pg-password-<id>` и удаляется в `finally` (`index.js:141-144, 183`).
- `main.js:236` `databaseUrl` ходит на `127.0.0.1`, `getPgClient` — на `localhost` (обе записи есть в `pg_hba`).
- Единственный сетевой вход — Node-сервер на `0.0.0.0:<hostPort>` (`main.js:370`), защищённый JWT; к базе напрямую с другого ноутбука не попасть.

### D8-001 · [Тяжесть 2] Встроенный Postgres с `--locale=C`: поиск по кириллице в упакованной программе чувствителен к регистру
- Направление: 8 · Класс: данные (расхождение dev ↔ упаковка)
- Окружение: упаковка
- Где: `electron/main.js:142` (`initdbFlags: ['--encoding=UTF8', '--locale=C']`), `electron/test-host.mjs:41` (то же); потребители — `server/src/controllers/occupancyController.js:80` (`"guestName" ILIKE`), `:86` (`mode: 'insensitive'`), `server/src/controllers/paymentController.js:198-200` (поиск в «Кассе» по гостю и номеру)
- Что: под libc-локалью `C` PostgreSQL сворачивает регистр только у ASCII: `lower()`/`ILIKE` для кириллицы не работают. Dev-база разработчика — `Russian_Kazakhstan.1251`, там всё работает, поэтому в разработке дефект невидим.
- Сценарий (гипотеза): администратор в упакованной программе ищет «асель» (или «АСЕЛЬ») в шахматке или «Кассе» — бронь «Асель Каримова» не находится; находится только точное совпадение регистра.
- Проверка: на dev-базе (эмуляция C-локали через collation): `SELECT lower('АСЕЛЬ' COLLATE "C"), ('Асель' COLLATE "C") ILIKE 'асель'` → `АСЕЛЬ`, `false`; без `COLLATE "C"` → `асель`, `true` (выполнено, MCP). В установленной программе: `SELECT datctype FROM pg_database WHERE datname='hotel_booking'` на 5433 → `C`.
- Последствия: «гость звонит, найти не можем» — ровно та боль стойки, ради которой делался поиск; у первого клиента (установка 05.09) кластер уже создан с `C`, смена локали требует пересоздания кластера (initdb) + перенос данных, а не миграции.
- Уже известно: нет
- Связано с: направление 3 (`/guests/lookup`, поиск в гриде), направление 6 (`PaymentsScreen`)
- Уверенность: подтверждено (SQL на collation `C`; сама установка на 5433 не опрашивалась)

### D8-002 · [Тяжесть 2] Падение Postgres не замечается, а закрытие программы после него зависает
- Направление: 8 · Класс: доступность
- Окружение: упаковка
- Где: `electron/main.js:456-471` (`stopHostProcesses`), `:889-896` (`before-quit`), `:874-880` (single-instance lock), `:473-486` (`waitForHealth` только при старте); `electron/node_modules/embedded-postgres/dist/index.js:224-226` (`close` слушается только внутри `start()`), `:236-260` (`stop()` ждёт `exit` уже завершившегося процесса); `server/src/app.js:93-95` (`/api/health` без проверки базы)
- Что: после старта за процессом `postgres.exe` никто не наблюдает; если он завершился (PANIC при нехватке места, антивирус, ручное убийство), сервер продолжает отвечать 503, а `/api/health` — 200. При выходе `pg_ctl stop` возвращает ошибку («не запущен») → `stopped=false` → `pgInstance.stop()` вешает `this.process.on('exit', resolve)` на мёртвый процесс и не резолвится → `before-quit` никогда не вызывает `app.quit()`; процесс без окон живёт, а новый запуск тихо гасится блокировкой единственного экземпляра.
- Сценарий (гипотеза): диск заполнился ночью, Postgres упал; утром администратор видит «Сервер временно недоступен», закрывает и открывает программу — она «не открывается».
- Проверка: запустить упакованный хост, убить `postgres.exe` в диспетчере, закрыть окно, проверить `tasklist | findstr "бронирования"` и повторный запуск. По коду: `index.js:246` регистрирует `on('exit')` после факта завершения — событие не повторится.
- Последствия: простой стойки до вмешательства «убить процесс в диспетчере»; телефонная поддержка.
- Уже известно: нет (план: «нет `uncaughtException` → при крэше main Postgres остаётся» — другой случай)
- Связано с: D8-006, D8-027
- Уверенность: предположение (по коду; живой прогон не делался)

### D8-003 · [Тяжесть 2] Ночная копия существует только пока запущена программа; пропуски не догоняются
- Направление: 8 · Класс: данные
